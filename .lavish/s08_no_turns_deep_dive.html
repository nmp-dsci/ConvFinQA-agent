The “no” turns

About one turn in fifty answers the literal string no to a question whose gold answer is a number. It is never right. It has survived five optimisation experiments, and it is not a hallucination — the calculator prompt instructs it.

The finding in one line.

The calculator prompt uses no — a value inside the legitimate answer space — as an out-of-band signal for “I cannot compute this”. A refusal is therefore indistinguishable from an answer, which is why it scores as wrong, reads as a preprocess fault, and cannot be fixed from any prompt except the calculator’s own.

The calculator did the only thing its contract allows. CalcOut is {answer: str} — there is no field in which to say “I could not compute this”, so the refusal has to be smuggled out through the answer.

02 · It is instructed, not hallucinated

This is the part that changes what to do about it. The behaviour is written into the calculator prompt, twice — and the second time, in the same sentence as the legitimate boolean answer.

calculator prompt (c2) · processing rule 1

… If any clearly required value is missing or mismatched (e.g., the current question asks for a single-year value but the only available answer is a multi-year total or a different metric), you cannot produce a numeric answer. In that case, the final answer is `no`. Do not guess.

calculator prompt (c2) · final answer formatting

For yes/no, which-one, or comparison questions: if the question can be answered with the available data, use the `greater` tool and then output `yes`, `no`, or the variable letter … as appropriate. If the question cannot be answered because the retrieved data is mismatched or insufficient, output `no`.
One token, two meanings, one sentence.

In that second passage no means “the comparison is false” and “I could not compute this”. Nothing downstream — not the scorer, not the attribution rule, not a human reading the CSV — can tell the two apart. Using an in-band value as an out-of-band signal is the whole bug.

The consequences follow mechanically:

  • It always scores wrong against a numeric gold. Confirmed: 0 of 5 correct, against 78.5% on turns where every operand was found.
  • It is invisible as a refusal. In every CSV, metric and trace it looks like the pipeline confidently answered a yes/no question.
  • It misdirects attribution. Gold-derived attribution walks triage → preprocess → retriever → calculator and stops at the first failing check, so a missing operand is filed against the retriever or preprocess — both of which are upstream, and neither of which chose to say no.

04 · Why five experiments missed it

This is not bad luck. Three properties of the loop conspired to hide it, and each is worth fixing on its own.

Attribution points upstream

First-fault attribution stops at the first failing check in pipeline order. A missing operand fails the retriever check, so the case is filed against the retriever — and the calculator, which chose the word no, is never reached.

The target is picked from fault counts

Because these cases are filed upstream, the calculator’s fault count stays low and it is never selected. Across five experiments: preprocess ×3, retriever ×2, calculator ×0.

A refusal looks like an answer

Nothing in the CSV, the metric panel or the gate distinguishes no-as-abstention from no-as-answer, so no report ever showed a refusal rate to notice.

The loop tried to fix it and failed — which is the confirmation.

Given the backfilled flip records, the c02-e02 prompt writer identified this failure mode by name and designed against it:

“Two prior rewrites (v6, v7) … were rejected: their collateral damage was concentrated in turns that went from a correct number to the degenerate non-answer “no” … So this rewrite deliberately does something different: it preserves v8’s spine … and adds only precondition-gated sections plus an explicit output-validity checklist.”

It wrote a preprocess rule against a calculator behaviour. The rate afterwards: 22%, unchanged. A correct diagnosis of the symptom, aimed at an agent that cannot produce it — because the loop only let it edit preprocess.

Naive fix: gain 1, lose 2, net −1 turn.

The two losses are the important ones. Double_STZ q0 asks “was the purchase price for hardy greater than for mondavi?” — gold program greater(1137.4, 1030.7). Preprocess planned subtract(A, B), the wrong program for a comparison, and the calculator overrode it and answered the question correctly. That override is a real capability, not an accident, and a fix that forces literal program evaluation would destroy it.

So the requirement is sharper than “stop saying no”. Any fix must simultaneously:

  1. make refusal expressible out of band, so it stops being scored and read as a boolean;
  2. preserve the calculator’s override on genuine comparison questions;
  3. not force evaluation when an operand is genuinely absent — those turns are unwinnable at the calculator, and belong to the retriever.

06 · The proposed fix

Three changes. The first is the actual fix; the second makes it visible; the third stops the loop mis-aiming at it again.

FIX 1

Give the calculator a way to abstain out of band

src/convfinqa/pipeline/stages.py

Add a field to CalcOut so a refusal has somewhere to live that is not the answer. answer stays a string so nothing downstream breaks; a refusal sets the flag and leaves the answer empty.

Backwards compatible: the field defaults to False, so existing readers, cached CSVs and the demo pack keep working. Only the calculator ever sets it.

FIX 2

Rewrite the two prompt passages — calculator c2 → c3

generated by evalloop propose

Remove no as a sentinel in both places, keep “do not guess”, and explicitly preserve the comparison override that saves Double_STZ q0 and Double_MRO q2.

FIX 3

Attribute an abstention to the calculator, and report the rate

evalloop/stage_scores.py

An abstention currently files against whichever upstream check fails first, which is how the loop spent five experiments upstream of the cause. With an explicit flag, first_fault() can name it, and the metric panel can carry a refusal rate so it is never invisible again.

  • Add calculator_abstained to the per-agent metric panel — a number that would have made this a one-look finding.
  • In first_fault(), when the calculator abstained and every operand was present, the fault is the calculator’s. When an operand was genuinely missing, keep it upstream — that is a real retriever miss and the attribution is right.

Sequencing

  1. Fix 1 + Fix 3 first, with no prompt change. They are pure instrumentation: they cannot change accuracy, and they turn the next run into a measurement of how often this actually fires.
  2. Then Fix 2 as one targeted experiment — --target calculator, gated normally. It would be the first experiment in either campaign to touch c2.

Running the prompt change first would confound the two: any accuracy move would be unattributable between the new contract and the new wording.

07 · Expected effect, stated honestly

I do not expect this to move accuracy much.

Of the nine cases in the champion run, five have a genuinely absent operand and are unwinnable at the calculator, one is a real arity failure, two are already correct, and one is recoverable. A realistic direct gain is one to two turns on 349 — roughly +0.3 to +0.6pp, which on this split is well inside the noise the gate is built to reject. It would very likely not promote on its own.

The case for doing it anyway is diagnostic, not numerical:

It stops corrupting the answer space

Two of the champion’s “correct” boolean answers are only correct because the refusal token happens to collide with the gold. That is luck being scored as skill in every report on the board.

It unblocks the next real experiment

~20% of every challenger’s collateral damage is currently this defect. Removing it makes the remaining flips a cleaner signal about the prompt actually being tested.

It stops the loop chasing a phantom

Two preprocess experiments have already been partly spent on it, including one that named it explicitly and could not fix it from where it was standing.

It makes the failure countable

A refusal rate in the metric panel converts “why do we keep seeing no?” from an investigation into a number on a dashboard.

If the honest expected gain being this small changes your mind about doing it, that is a reasonable conclusion and I would rather you reach it from the real number than from an optimistic one.

08 · Risks & what I need from you

Risk · the override is fragile

The comparison override that saves two turns is undocumented behaviour — the calculator deciding to answer a boolean despite being handed subtract(A, B). Rewriting the prompt around it could disturb it. Mitigation: the two cases are named, and the gate would catch a loss. But two turns is inside the noise, so the gate might not catch it.

Risk · changing a schema mid-campaign

CalcOut is read by the runner, the demo pack and cached CSVs. The new field defaults to False so nothing breaks, but serving/demo_pack asserts its events match turn_events exactly — that contract needs re-checking before shipping.

Risk · abstention could get more common

Making refusal cheap and legitimate might make the calculator refuse more often, trading wrong answers for no answers. Both score identically, so it would be invisible in accuracy but real in usefulness. The new refusal-rate metric is what would catch it.

Non-risk · the 5 missing-operand turns

Worth being clear: this fix does not recover those. They are retriever misses — in the traced case the document does contain the 2018 figure and the retriever said it did not. That is a separate piece of work.
