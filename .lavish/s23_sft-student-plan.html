02 · Getting the data right, by whole conversation, with test kept out

The unit is the conversation. Every set holds whole conversations. A training row is one conversation with all of its questions, in order, answered in one Sonnet 5.5 session. No conversation is cut short, split into turns or split across sets. A conversation that fails a gate on any question is dropped whole, never trimmed. The page rule below only decides which conversations may enter which set.

The prompt loop split by conversation id. That isn't enough for training weights: ConvFinQA builds Type II conversations by joining two Type I conversations from the same report page. Double_AAL/2015/page_74.pdf is in test, and its half Single_AAL/2015/page_74.pdf-2 is not. Training on the second would show the student a test document and some of its questions. So this plan splits by page, normalising ids by dropping the Single_/Double_ prefix and the -N suffix. The same rule keeps out eval_loop_v1's sealed holdout.

Five leak guards, each one a test

  1. The sft_v1 manifest refuses any train or val conversation whose normalised page belongs to a test or sealed-holdout conversation.
  2. The row builder refuses any CSV whose split is test, and the Sonnet 5.5 pass takes only page-clean ids.
  3. sft/checks.py scans every row for any test or holdout report id, page or question, before upload and in CI (tests/test_sft_no_leak.py).
  4. The training job checks train.jsonl's sha256 against the committed data card before it loads the model (tau's rule).
  5. The pre-registration file (train set sha, sampling, verdict rules) is committed before the first test pass. The epoch is picked on val and written down first.

Two side findings, recorded and not changed. The prompt loop's draw_train leaves out the test report ids but not their page siblings: 6 of the 196 conversations in sdk_v1·Sonnet 5's committed train draws share a page with a test conversation. It also doesn't leave out eval_loop_v1's sealed holdout. v2 records its own holdout as "the untouched remainder of the pool", so v1's 56 are back in the pool it draws from, and the same two draws contain 3 of them. Making draw_train page- and holdout-aware would change which ids each seed produces, and break both the id-for-id reproduction challenger pairings depend on and the superset property your 600 extension relies on. So I recommend recording both in CLAUDE.md. This plan filters after the draw, without moving a single drawn id.

03 · Step 1, Sonnet 5.5 answers every question of the 600

  • What runs: sdk_v1 · claude-sonnet-5-5 · high, the champion's prompt and effort on the newer model. It runs on the 552 page-clean conversations of draw_train(seed=2027, n=600): the 95 page-clean ones from the committed 100, and 457 from the extra 500. Sonnet 5.5 answers all 600 (minus the 48), because the training data is 5.5's.
  • In full. There is no --stop-at-first-wrong: every question of every conversation is answered, so a kept conversation is complete.
  • On the subscription only. A session limit leaves turns unscored and the pass is finished with --resume-from after the reset, never by switching billing.
  • Two new trailing columns, because the filter needs them and the CSV doesn't hold them today: sdk_attempts, the number of tries a turn took (it is only in the trace now), and sdk_thinking, the thinking blocks the SDK returns. The runtime currently drops them; SDK 0.2.152 exposes them as ThinkingBlock.
  • A by-product: the 95 shared conversations give a paired, per-conversation read on Sonnet 5.5 against Sonnet 5 on train.

Smoke first. This repo's Agent SDK is 0.2.152. Its bundled CLI didn't recognise claude-haiku-5-5: it served it anyway and priced it on a fallback card. A 3-conversation pass checks that Sonnet 5.5 is served as asked at effort high, that the output contract holds, and whether thinking blocks come back. If the CLI misprices it, tracking/cost.py gets Sonnet 5.5's published rate before any cost is recorded. If the model isn't served, I stop and report.

Cost uses Sonnet 5's committed full test pass, $11.83 and 13 minutes for 349 questions. That puts 1,993 questions at ≈ $68 API-equivalent of quota and ≈ 75 minutes, until 5.5's own rate is measured.

Two checkpoints are defined differently from the stage panel, for measured reasons. Raw operand recall reads a value carried from an earlier answer as "missing", which marked 45 of 278 correct turns in the seed-2027 draw. The panel's plan check compares with the rounded gold answer at 1.5%, so it rejects an exact multiply(divide(A, B), const_100) = 1.748 against a gold of "1.7%". With the panel's definitions the same draws keep 50 instead of 117. No CSV row is edited: a kept conversation is exactly what Sonnet 5.5 did.

05 · Step 3, a reasoning-first layout built for supervised fine-tuning

The SDK runtime records a turn in the order the harness needs it: tool calls first, then a JSON answer with the reasoning inside it, after the fact. For SFT the order matters, because each token is learned conditioned on the tokens before it. So each kept turn is laid out reasoning, then action, then answer, and every reasoning line is one the gates have already verified. The content is Sonnet 5.5's own; only the layout is new. Why this layout

  • Causal order. The plan is written before the tool call it drives, so the model learns to decide and then act, not to justify afterwards.
  • Verified reasoning only. The turn type, operands, sources and plan lines are fields G2–G5 and T4 have checked against gold, so the model never learns a wrong step that happened to land on a right answer.
  • Grounded. Every operand carries its source cell or earlier turn, which trains exactly the champion's main remaining failure: the wrong row or period.
  • Short and consistent. About 100–250 tokens per turn, the same shape every time. A 4B model copies length and habit, so a compact, regular block is easier to learn than free prose.

What's trained on

  • Loss on assistant tokens only (assistant_only_loss): the reasoning block, the tool calls and the final JSON. The prompt, document, questions and tool returns are context.
  • Whole conversations. Each turn is learned with the conversation's earlier, correct turns in context, exactly as at inference.
  • The same layout at inference. The student runtime accepts text before a tool call and parses the final JSON, so train and test formats match. The base gets the same prompt and harness, so the comparison is fair.
  • Mask read back on every row before step 1 of training (tau's check, which caught 273 misaligned rows there).
