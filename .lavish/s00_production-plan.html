Architecture review & delivery plan · 27 Aug 2026

ConvFinQA Production Plan

The research core is done and the numbers are real — a four-stage agent pipeline at 77.1% held-out execution accuracy, with a committed eval cache and a self-improving prompt harness. What is missing is everything that makes it an operable product: deployment, auth, resilience, experiment tracking, and gates. Both of those halves already exist in this portfolio — the siblings solved production, this repo solved the model. The plan is to merge them.

01 · Where it stands

The system today

Every turn of a conversation runs a four-stage pipeline over DeepSeek v4-flash. Triage classifies the turn; number turns take a two-call path, program turns a four-call path ending in a tool-calling calculator over the six ConvFinQA DSL operations. Two backends implement the same stages: Pydantic AI is the serving path, DSPy exists for GEPA optimization.

Around that pipeline sits an unusually strong research apparatus: a cached eval harness whose outputs are committed to git (v1/v2/v3_1 reproduce with zero API calls), two GEPA optimization runs in runs/, and the s7 diagnosis harness — a Diagnose → Route+Fix → Verify loop that mines failing cases into per-agent prompt rules and regenerates prompt variants. The serving layer is a FastAPI app (sessions, SSE streaming ask, eval read APIs) with a React chat + eval-explorer frontend.

Headline results, on the 770-question held-out sample the optimizer never trained on: v1 73.0% → v2 (GEPA) 77.1% → v3_1 (s7) 76.2%. v2 is champion; v3_1 is a published negative result worth keeping visible — the harness worked mechanically, but rules verified against single cases over-fitted.

03 · Target architecture

One image, two modes

Both siblings converged on the same doctrine, and ConvFinQA should adopt it wholesale: build one container image that carries everything pre-computed, and let a single environment flag decide whether the LLM exists. Dev runs the full system with keys from ~/.env; the public AWS deployment runs the identical image with DEMO_MODE=1 and no keys at all — the gate is belt-and-braces because there is nothing to steal.

ConvFinQA is the easiest of the three to deploy this way: it has no database. The dataset, prediction CSVs, replay packs, and MLflow export are all files, so the transcript-rag-agent pattern applies directly — one App Runner service, frontend dist/ served by FastAPI, no VPC, no Aurora, no Secrets Manager.

Why this shape wins It is the proven pattern one directory over: data-qa-agent runs DEMO_MODE through a single LLM choke point with recorded replay packs baked into the image; transcript-rag-agent deploys keyless to App Runner with a deny-by-default method gate and everything pre-computed. Reusing their Terraform bootstrap, tfstate bucket, OIDC role pattern, and smoke-test discipline cuts this from a project to a porting exercise.

04 · Demo mode

Replay, don't fake

The demo must feel like the real product. The trick both siblings use: record real LLM sessions in dev, ship the recordings in the image, and replay them through the same SSE frame types the live path emits — the frontend cannot tell the difference. ConvFinQA is uniquely well-positioned: stream_turn already emits typed events (stage_start / stage_output / tool_call / tool_return / answer), and every committed prediction row already carries full per-stage IO. The demo pack is nearly free.

Mechanism

  • One flag, one choke point. settings.demo_mode, checked in a single module every LLM call passes through — a _demo_blocked() that raises 501 not_available_demo. Handlers cannot route around it. Tested both ways ("LLM functions untouched outside demo").
  • Recorder. A demo_pack CLI exports selected recorded conversations (per showcase report: question, per-stage IO, tool calls, final answer) into PR-reviewed JSON under src/convfinqa/serving/demo_pack/. Curate 6–10 reports that show off number turns, multi-step programs, and cross-turn reference resolution.
  • Replay. In demo mode, ask/stream resolves the question against the pack for the active report — exact gold-question match first, fuzzy (SequenceMatcher + Jaccard blend, honest miss below threshold) second — then synthesizes the same event sequence, paced at a few hundred ms per stage so a real 30–60 s turn plays in ~4 s.
  • Keep the non-LLM half genuinely live. Report browsing, document viewer, gold questions, the eval explorer, and the admin portal all read committed files — they stay fully functional, which is what makes the demo honest.
  • Frontend: flag, don't hide. /healthz reports mode: demo; a DemoGate wraps free-composer input in a real <fieldset disabled> with a "demo replay" chip, and steers users to a chip rail of available showcase questions (GET /demo/questions). Stable error codes (not_available_demo, demo_rate_limited, demo_full) map to friendly copy.
  • Abuse controls (cheapest check first): global in-flight concurrency cap → per-IP sliding-window limits (in-memory is correct here because App Runner max-size=1) → method-level deny of writes. Session TTL eviction already exists.

05 · Experiment tracking

MLflow as the system of record

MLflow is already a declared dependency — it has just never been called. The design principle (from the production playbook material): version the whole bundle together. A "model version" here is not a model checkpoint — it is a prompt bundle:

bundle = {
  prompts_version:  "v2",                      # or variant, e.g. v3_1
  gepa_overlay:     "gepa_real_20260502_005251" | null,
  lm_mini:          "deepseek-v4-flash",
  lm_max:           "deepseek-v4-pro",
  dataset_hash:     sha256(convfinqa_dataset.json)[:12],
  code_sha:         git short sha,
}

A small bundle_fingerprint() module computes this once and stamps it everywhere: every MLflow run, every prediction CSV, every serving session (data-qa-agent's agent_version.py is the template — every answer attributable to the exact build that produced it).

What gets logged

  • Eval runs (evaluation/runner.py) — one MLflow run per version scored: bundle params; metrics = overall accuracy + every slice already computed (turn_type, conv_type, question order); artifacts = the prediction + joined CSVs and the HTML report.
  • GEPA runs (optimization/gepa.py) — params (mode, metric-call budget, train/val sizes), the val-score trajectory as step metrics, optimized_runner.json as an artifact. Backfill the two committed runs in runs/ so history starts populated.
  • s7 harness runs (diagnosis/harness.py) — cases diagnosed / resolved / unresolved as metrics, promoted-rule counts per agent, rules + attempts JSONL and the diagnostic HTML as artifacts.
  • Registry. Register convfinqa-pipeline; each version is a bundle; aliases champion (v2 today) and challenger. Promotion is not a click — it requires the regression comparator to pass: overall accuracy ≥ champion AND no per-question pass→fail flips. "Fixed number turns, broke programs" can never score as a win.

The promotion lifecycle

The full loop, end to end — this is the contract the registry enforces:

  1. Every new bundle is registered — whether it came from hand-edited prompts, an s7 auto-research round, or a DSPy/GEPA run. Its full spec (params, prompt sources, optimizer artifacts) is captured at registration and never deleted — past champions and failed challengers keep their spec and eval artifacts forever.
  2. It is evaluated on the same 770-question held-out set the optimizer never saw, producing a scored MLflow run linked to the version.
  3. The comparator decides promotion. The first version becomes champion by default; after that a challenger is promoted only if overall accuracy ≥ champion and no per-question pass→fail flips. (Strictly "beats the champion" is not quite enough — the flip check is what stops "fixed number turns, broke programs" sneaking through.)
  4. Promotion is an append-only event — an alias move recorded with timestamp, comparator verdict, and the runs it was based on. The registry view shows the whole promotion history; nothing is overwritten.
  5. History is backfilled once, then captured automatically. v1/v2/v3_1 evals and both committed GEPA runs are reconstructable from git and get backfilled in Phase 2. Everything after that is captured by construction, because logging lives inside the eval/GEPA/s7 runners themselves — not in operator discipline.

Backend: file store, not a server. file:./mlruns locally (gitignored, like .dspy_cache). For the demo, an export step writes a compact mlflow_snapshot.json (runs, params, metrics, no heavy artifacts) that is committed and baked into the image — the admin portal reads the snapshot in demo mode and the live store in dev. No tracking server to run, secure, or pay for.

06 · Frontend

The product surface of a gen-AI system

The existing React app (chat + eval explorer, Zustand, SSE streaming) is a solid base, but the target is a frontend where you can see how the agent works, not just talk to it. Five surfaces:

Chat — ask the agent

  • Select a report, then ask. The existing flow stays: pick a financial report (ReportPicker), then either type free-form questions or run the conversation's preset gold questions from the dataset turn by turn — the run-all-gold batch mode the app already has — watching the four stages stream. Live against the champion bundle in dev; replayed from packs in demo.

Traces — how the agent is working

  • Every agent run is traced and browsable. A lightweight run-trace store (SQLite/JSONL) persists what the capture dict already produces — per-stage input/output/reasoning, tool calls, plus tokens and latency per stage — for every serving turn and every eval-run row. Logfire stays the deep external trace; this is the in-app view.
  • Trace viewer — pick any conversation turn (live session or eval run) and see the stage timeline: triage decision → preprocess plan → retrieved values → calculator tool loop → answer, with gold comparison where one exists. This is the "why did it answer that" surface.

Data & answers explorer

  • Dataset splits made visible — the train sample (200 conversations the optimizer saw), the 770-question held-out set, and each conversation's membership clearly badged. The held-out discipline becomes something you can point at, not just claim.
  • All the answers — per conversation: every question, gold answer + program, and each version's predicted answer/program side by side (v1 / v2 / v3_1 / …), with correct/incorrect marks and a link into the trace for that turn. Fully live in demo — it all reads committed CSVs.

Experiments & model versioning — champion / challenger

  • Experiments table — every MLflow run (eval / GEPA / s7), sortable, with bundle params, headline metric, and status; served by /admin/experiments endpoints that read the live store in dev and the baked snapshot in demo.
  • Accuracy trend — overall + per-slice accuracy across versions, the champion marked; the honest chart that shows v3_1 dipping.
  • Run detail & diff — params, all slice metrics, links into the prediction viewer for the exact CSV behind the run; side-by-side diff of two runs with per-slice deltas and the pass→fail flip list.
  • Registry view — bundle versions with champion/challenger aliases and promotion history; promote is owner-gated in dev (and only enabled when the regression comparator passes), visible-but-inert in demo.
  • Rules browser — the s7 rule stores per agent (rule text, verified-on case, attempts), currently only visible by reading JSONL.

Research console — dev only

  • Kick off a round of auto-research from the app: launch an s7 diagnosis round (with limit/retry knobs) or a GEPA smoke run as a background job — POST /admin/research/start, owner-token gated, one job at a time, progress streamed over the same SSE machinery the chat uses.
  • Results land as MLflow runs and appear in the experiments tab as the new challenger; the demo shows the console with completed rounds and their outcomes, launch controls inert.

Landing page — the front door in both modes

Modeled on the siblings' entry pages: a standalone landing route that presents the project before the app — name, one-line pitch, the headline metric (73.0% → 77.1% held-out), and cards for what is inside (chat, data & answers, traces, experiments, research). It reads /healthz at runtime, so the same build adapts to the deployment with no rebuild:

  • Dev: "Open app" goes straight through to the live product — ask questions against any report, launch auto-research rounds from the research console, inspect traces and experiments; admin writes unlock with the owner token.
  • Demo: an "Enter demo" card explains what is genuinely live (splits, answers, traces, experiments) and what is replayed (chat), then opens the same app read-only — every function visible, all write and launch controls inert behind DemoGate, with a discreet owner sign-in kept off to the side, like data-qa-agent's hidden owner door.

A mode chip stays in the header throughout the app; the composer gets the DemoGate treatment and a showcase-question chip rail per report in demo.

Production build path

FastAPI mounts frontend/dist (SPA fallback to index.html) so one container serves everything; VITE_API_URL becomes same-origin and the dev-only Vite proxy list stops being a production concern. Fix the Playwright webServer command while in there.

07 · CI/CD

The ship path

The current CI (tests + frontend build) grows into a gate wall on every PR, and a deploy workflow on main. The load-bearing addition is the offline eval-regression gate — the pattern from transcript-rag-agent's test_committed_runs.py: because prediction CSVs are committed, CI can re-score them deterministically with zero API calls and fail if the champion's floor regresses or any case flips pass→fail. A prompt change that silently degrades 77.1% cannot merge.

One deliberate improvement over the siblings: their deploy workflow does not depend on CI passing. Chain them here (workflow_run or a shared job) so a red main cannot ship.

08 · AWS footprint

Small, keyless, alarmed

Copy transcript-rag-agent's demo stack nearly verbatim — it is the minimal footprint that still counts as a real deployment:

  • ECR private repo, lifecycle policy keeping the last 5 images (short rollback window, not an archive).
  • App Runner — 1 vCPU-class small instance; ConvFinQA has no torch/embedding stack, so 512 CPU / 1 GB should hold comfortably (verify RSS after baking the 21 MB dataset + packs; record the measured number in the tf comment, as the sibling does).
  • No VPC, no database, no Secrets Manager — the container is read-only by construction and holds no keys.
  • Terraform under infra/terraform/{bootstrap,demo}, reusing the existing tfstate bucket and OIDC/IAM role pattern (same AWS account, new role + state key). Defaults in variables.tf are the live config — tfvars stays local.
  • Alarms: 5xx alarm (>10 over 10 min) + the account billing alarm. X-Ray off; Logfire covers tracing if a token is ever added — the demo can run without it.
  • Cost: the sibling's identical stack runs at roughly $5–15/month (App Runner smallest instance + ECR storage + data egress). Demo mode itself is the biggest cost control — zero inference on the public deployment, by construction.
