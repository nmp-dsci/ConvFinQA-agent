s10 · plan for review · branch agent-sdk-experiment · 2026-09-05

One Claude Agent SDK agent, its own teacher loop, and a fair fight with the pipeline

Build three agents: a qa_agent on the Claude Agent SDK (built the way data-qa-agent/sdk_agent.py is built) that does the whole triage → preprocess → retrieve → calculate job in one session with a calculator tool; a diagnosis agent that reads its wrong answers; and a teacher agent that rewrites its prompt. Run the optimisation loop on it, then make the comparison that is actually fair — the optimised DeepSeek pipeline (v8) against the optimised SDK agent — on the same gate split, the same evaluator, the same one-sided McNemar rule, published in MLflow.

The verdict that counts is optimised vs optimised. The first SDK-vs-v8 pass (P3) is diagnostic — it seeds the teacher loop, it does not decide anything. The headline comparison is P6: best SDK prompt after its campaign against v8, which already had its campaign. This plan does not touch serving, the demo, or the pipeline's champion alias; the SDK agent gets sdk_champion. If it wins, replacing the runtime is a follow-up with its own plan.

01 · Goal and the baseline it has to beat

Kept identical on purpose

  • Split manifest eval_loop_v2, gate = test100, train resampled per cycle.
  • COLUMNS in evalloop/runner.py, stage_scores.score_rows, first_fault, flips.json, the McNemar gate in tracking/comparator.py.
  • The six calculator tools in pipeline/tools.py — same functions, registered on an MCP server instead of calc.tool_plain. Arithmetic happens in the tool, never in the model.
  • The knowledge in the four prompt texts — distilled into one SDK prompt, not copied (§03). The rules survive; the inter-agent plumbing does not.

What actually changes

  • Control flow moves from Python (turn_events) into the model: it decides when it has enough and in what order to call tools.
  • History is the session, not a rendered history_text block — the model sees its own prior tool calls and answers.
  • Model: Claude Sonnet 5 via the claude CLI subprocess, not DeepSeek in-process — a confound the plan addresses in §08.
  • Stage outputs are reported by the model in its structured result instead of being typed agent outputs; nothing forces the order. A program turn that reports no plan, or answers with no calculator call, is a recorded fact and a metric.

03 · The SDK agent contract

Mirrors data-qa-agent/sdk_agent.py: a lazy SDK import, an in-process MCP server built with sdk.tool(name, desc, schema)(handler) and create_sdk_mcp_server, ClaudeAgentOptions assembled in one place, and a stream driver under contextlib.aclosing with a token-budget abort. The differences are a much smaller tool set and the fact that we drive a multi-turn session rather than one question per run.

Tools on the cfq MCP server — the calculator, nothing else

ToolArgumentsHandler doesFeeds

ALLOWED_TOOLS is exactly these six and nothing built-in — no Read, Bash, WebSearch. Triage, planning and retrieval are things the model does itself against the report in its context and the turns already in the session; they are not tools. The document is in the prompt (mean 4.3k chars, p90 6.3k, max 8.1k across the gate split), so the workspace-and-Grep pattern the sibling uses for large data has nothing to search here.

The train of thought, and how it is captured

What the prompt asks for

numbertriage → retrieve: decide it is a lookup, find the value in the report (or a prior turn), answer
programtriage → preprocess → retrieve → calculate: decide it needs computation, write the sub-questions and the program, pull each operand from the report or prior answers, then run the program through the calculator tools — never in-model arithmetic

Structured result = the stage record

output_format json_schema:
  turn_type:     "number" | "program"

Written by backends/agent_sdk.py into the same capture keys turn_events uses (triage, preprocess, retriever, calculator), so _capture_to_row_fields, the panel and first-fault attribution run unchanged. The model reports its stages; nothing enforces them, and a program turn with an empty program or no calculator call is counted (sdk_stage_skips) and attributed to the stage it skipped.

System prompt: distilled from the four, then owned by the loop

The four v8 prompts total ~22k characters and were written for four stateless agents passing [[ ## name ## ]] blocks to each other. Copying them into one prompt would carry that plumbing into an agent that has none of it. Instead the first SDK prompt is a distillation: the domain rules, the turn-type criteria, the reference-resolution rules for prior turns, the retrieval conventions (units, signs, table-vs-text) and the calculator discipline, rewritten as one document with the train of thought as its spine.

prompts/sdk_v1.py            # SDK_PROMPT: str — the distilled prompt, versioned as ONE lineage
  1. Role and the two turn types
  2. Train of thought: number → triage, retrieve · program → triage, preprocess, retrieve, calculate
  3. Distilled rules per stage (from TRIAGE / PREPROCESS / RETRIEVER / CALCULATOR of v8)
  4. Calculator tools: always, never in-model arithmetic; program notation matches gold DSL
  5. Output contract (the structured result above)

Who writes it is Decision D8: the teacher agent produces the first draft from the four v8 prompts plus the dataset notes in CLAUDE.md, and I review and trim it before it becomes sdk_v1; or I write it by hand. Either way it is committed once, hashed, and from then on only the teacher agent changes it — the SDK prompt gets its own lineage in registry.json → sdk_prompts (sdk_v1, sdk_v2, …; hash is truth, seq is the handle), separate from the pipeline's per-agent compositions. Run names carry it: sdk-evalloop-test100-sdk_v3-<stamp>.

Session shape and the final answer

One session per conversation

turn 0user message = report text + table (rendered as today's _DOCS[report_id]) + Q0
turn nuser message = Qn only; the session already holds the document, prior tool calls, prior answers
resultoutput_format = json_schema above; ResultMessage.structured_result is the prediction plus the stage record, total_cost_usd and token counts go on the span
budgetmax_turns ≈ 8 per question — a 3-step program is ≤ 3 tool calls plus the answer (sibling uses 22 for a much larger task); abort the conversation on a token ceiling, mark remaining turns as error rows like the pipeline does on call_with_budget exhaustion

Why not one session per question

The pipeline re-renders history_text every turn because its agents are stateless. The point of the experiment is to let the agent use the context it already has — cross-turn reference resolution is the paper's hardest failure class and the pipeline's weakest (Type II 63.3%). Per-question sessions would re-create the pipeline's constraint and measure nothing new.

The cost is that a bad early turn contaminates later ones inside the session the same way it does in gold — which is the actual task.

05 · The eval loop: question → agent → diagnosis → teacher → experiment

Both arms run the same loop. The pipeline already has it (teacher.py: diagnose → propose → targeted gate, Opus 5 on the Agent SDK); the SDK arm gets its own pair of loop agents because what they read and what they write differ: the diagnosis agent reads one agent's reported trail and tool trajectory, and the teacher rewrites one prompt instead of one of four. The loop ends in the same place for both — an optimised champion — and those two champions are what the final full eval compares.

What the diagnosis agent checks, stage by stage

Step 1 is deterministic and runs before any LLM: stage_scores compares the row to gold and produces the flags below plus a first-fault stage. Step 2 is the agent: with those flags in hand it reads the report (table + text), the message history, the question and the qa_agent's own trail and calculator trajectory, and writes the why — which cell or sentence should have been used and which was, which prior turn a reference pointed at, whether the plan's operator or operand order was wrong, whether the answer was right but failed numeric match. It cannot contradict a flag without saying so (gold_suspect).

Per case the agent emits stage (the first one that broke), label (taxonomy), evidence (quoted from the document or history) and fix_hint — one summary of why, anchored on where.

Three append-only ledgers: diagnoses → rewrites → gates

Today each diagnose pass writes its own diagnoses_<version>_<stamp>.jsonl holding only the model's output, the teacher's output is a prompt module plus a diff on an MLflow run, and the campaign memory (evalloop/ledger.py) is reconstructed by searching MLflow runs. Replaced by three flat JSONL ledgers under evaluation/diagnostics/evalloop/ that both arms append to — diagnoses.jsonl (one line per diagnosed case), rewrites.jsonl (one line per edit the teacher made), gates.jsonl (one line per gate verdict) — joined by ids so one query traces a case from the failure that was seen, to the edit it motivated, to what the gate said about it. Every line in a file has the same columns; nested values are JSON strings so a row stays one row; pd.read_json(path, lines=True) is the table. Nothing ever rewrites or reorders a line.

MLflow: the same rows, on the run that produced them

Every diagnose, propose and gate run logs the exact lines it appended as a ledger_rows.jsonl artifact (same columns as the file), tags kind, runtime, campaign, rewrite_id / gate_id, and mirrors the scalar columns as params (base_version, new_version, hashes, failure_classes) and metrics (n_edits, n_diagnoses, delta_pp, p_value, fixed, broken, cost_usd) so the MLflow UI can chart them over run time and a run can be found from a ledger id. The file ledgers are the source; evalloop/ledger.py's MLflow-search memory becomes the fallback when the files are absent, not the primary. Traces stay as they are (run → report → question → stage → LLM call) and carry the same ids as tags, so a span, a run and a ledger row point at each other.

Rules

  • Append-only, all three. evalloop/ledgers.py::append(name, rows) opens with "a", writes, fsyncs. No function in the codebase rewrites a ledger; a test asserts line counts only grow across a diagnose, a propose and a gate call.
  • Schemas frozen, extension by adding columns at the end. One COLUMNS tuple per ledger in the module; new columns get a default so old lines still load into the same frame ("stackable" means every past row is still a row of today's table). Pinned by tests/test_ledgers.py.
  • Committed, like every other evaluation/diagnostics/ artefact — the ledgers are the history the story reads. Each run also logs the lines it appended as its own MLflow artifact, so the run view shows just that pass.
  • Outcomes are new rows, never updates. The teacher references diagnosis_ids, the gate references a rewrite_id; "what happened to this case after the rewrite" is a join, not a column that gets updated in place.

What it replaces, what it feeds

  • The per-run diagnoses_*.jsonl files stop being written; teacher.py::diagnose_run / propose_version and gate.py (pipeline arm) append to the same ledgers — small additive changes, in scope for P4 so both arms' history sits in the same tables from campaign s01 onward. Backfilled once from what exists: the three diagnosis files, the propose runs' diffs and the gate runs' flips.json in MLflow, tagged runtime=multi_agent.
  • prior_diagnoses and ledger.diagnoses_for_agent / attempt history (the teacher's memory) read the files filtered by runtime and prompt hash instead of searching MLflow.
  • κ scoring reads the ledger; the labelling sheet is a filtered export of it.
  • The Dataset page gets a "diagnoses" tab: the ledger filtered by report_id, so a suspect gold label shows every diagnosis that ever touched it.

What the teacher agent does with the whole run

multi_agent · four prompts, one moves per cycle

The teacher receives all diagnoses, ranks failure classes (Wilson bound over pooled draws), and rewrites one subagent's prompt for the top class. That rule exists because four prompts are four lineages: gate-targeted judges the change on that agent's own panel metric, and the promotion record says exactly which lineage moved. Unchanged in this plan.

agent_sdk · one prompt, several areas per cycle

The teacher receives the same diagnoses, but there is one prompt, so it may edit several areas at once — the triage criterion and the reference-resolution rule and a calculator example — one edit per failure class it decides to address. This is the one-prompt advantage: a cycle can act on everything the run showed, not just the top class. Each edit is tagged with its class and the case ids behind it, and the change list is attached to the run beside the diff.

Review of the multi-area approach — agree, with two guardrails. The cost of editing several areas per cycle is attribution: when the gate says +3pp you don't know which edit paid, and when it rejects you don't know which edit broke it. The gate still measures the whole prompt, so promotion stays sound; what changes is how a rejection is read. Guardrail 1: the teacher's change list is per-class, and flips.json already records every pass→fail and fail→pass by first-fault stage — so after each gate the story reports, per edit, the flips in its own class. An edit whose class got worse is reverted by the next teacher pass (it is told). Guardrail 2: the two-consecutive-rejections rule applies to the lineage, not to a class; if two multi-area rewrites in a row fail the gate, the campaign drops to one area per cycle for the rest of it. The per-agent panel keeps working because the qa_agent reports its stages, so "which area regressed" is readable even without isolating edits.

What is different, and why

The unit of change is the prompt, with per-class edits inside it. The pipeline's "one subagent per experiment" rule is replaced by "one tagged edit per failure class, all in one lineage" — see the review above for what that costs and how it is kept honest.

Skipped stages are failures of that stage. A program turn with an empty program attributes to preprocess; one with no calculator call attributes to calculator. Pinned by a test before the first cycle.

Same caps. MAX_EXPERIMENTS = 5, MAX_CONSECUTIVE_REJECTIONS = 2 (on the lineage); campaign s01 in the ledger, its own row on the Campaigns page.

The comparison at the end is full and symmetric. Both arms get a full test100 pass with their optimised champion — v8 as committed (D7) or re-run, sdk_champion fresh — and the paired McNemar comparison plus the per-stage panel side by side is the write-up's headline (P6).

08 · Risks and confounds

confound Model and architecture change together

v8 runs DeepSeek v4-flash; the SDK agent runs Claude. Optimised-vs-optimised makes the comparison fair on effort, not on model. A win says nothing about "one agent vs four" unless the pipeline also runs on the same Claude model once (D2). Recommend it — it is the difference between a result and an anecdote.

throughput CLI subprocess per conversation

Each session is a claude process. At concurrency 4 a test pass is an estimated 25–35 min versus 344 s. Fine for an experiment; it is the main reason serving is out of scope here.

billing Subscription limits and terms

The subscription path (like the sibling) hit rate limits twice yesterday on teacher traffic alone; a 349-question pass is ~10× that. The API path costs money but is predictable and is what a replacement runtime would ship on. Also verify the subscription terms permit automated eval load before leaning on it.

stats Gate split has been used ~10 times

test100 has judged every campaign gate since 2026-09-03. Selection bias is mild for a paired test between two arms that both see it once, but the holdout (D6) is the only clean confirmatory read left.

validity ConvFinQA is public

Any frontier model may have seen the dataset. Report it, don't pretend otherwise; the paired comparison is still fair because both arms face the same exposure risk — but the absolute number is not a generalisation claim.

behaviour The model may skip stages or do arithmetic in its head

Nothing forces the trail. sdk_stage_skips counts program turns with no reported plan or no calculator call; sdk_inline_arithmetic counts answers that don't match any tool return. High counts are a finding about the prompt, not a bug to hide — and the preamble is the only text hand-tuned to bring them down.

repro Non-determinism

Neither arm is deterministic. The gate's bootstrap CI absorbs it; the commit-the-CSV rule means the number in the write-up is the number in the store.

scope Serving is untouched

If the SDK wins, wiring it into turn_events events, DEMO_MODE (no key, recorded pack) and API-key billing in the container is a separate plan. Nothing here changes what ships.
