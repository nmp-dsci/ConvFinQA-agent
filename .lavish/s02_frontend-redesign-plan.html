01 · Goal, current state, gap

What the redesign has to deliver

Your requirements, as stated

  1. A demo page as the landing page, working in dev and in production.
  2. In production a visitor gets demo mode only: the chat interface, their previous chats, and the admin portal showing the evaluations that were done.
  3. The portal shows production metrics and evaluation / optimisation metrics.
  4. A system plan / debrief page so anyone can understand the complete structure of what was built.
  5. A rubric for what makes a good demo-into-chat frontend, informed by how other AI engineers build, then two options.

Who opens the link

The portfolio context (ai-engineer-fit/) names the gaps this project exists to close: Technical presentation / demo skills (48%), Model evaluation / monitoring (40%), React (20%). Two readers, two clocks:

  • The skimmer — recruiter or hiring manager, ~20 seconds, wants one intuitive number and something moving.
  • The engineer — will interview you, ~5 minutes, wants to see the traces, the eval discipline and how it was shipped.

Found while measuring: live serving is broken in dev today

DeepSeek v4-flash now defaults to "thinking" mode, and that mode rejects the tool_choice pydantic-ai sends for every structured output_type. The first stage of any live turn returns 400 "Thinking mode does not support this tool_choice". I verified the fix with a raw request — adding "thinking": {"type": "disabled"} to the body makes the same call succeed — and used it as a scratch-only override to measure the numbers on this page. It is a one-line change in llm.py::get_model (settings=ModelSettings(extra_body=…)) plus a test. Until it lands, dev chat, convfinqa-eval and the s7 harness all fail on their first model call. The public demo is unaffected — it makes no model calls. Decision at the bottom of the page.

02 · What the research says

How the engineers in the transcript corpus actually build frontends

Method: 29 queries (18 semantic via MiniLM, 11 BM25) over the transcript-rag-agent store — 4,542 chunks from 135 videos — then full-text reads around the strongest hits. 41 videos surfaced; 14 speak directly to frontends, demos, or what a reviewer needs. Each finding below carries the channel, talk and timestamp so you can open the clip.

1 · The stack consensus is React + Vite + shadcn/ui, FastAPI behind it

"A combination of three things that I recommend: React, Vite, and shadcn UI… you import that code into your project. So rather than it being stored in your node_modules and being a dependency, you import that code into your project. So now your coding agents can also start to work with it."

Dave Ebbelaar — The Best AI Automation Stack to Learn in 2026 @6:56–9:02 · also Build a Full-Stack GenAI Project in 4 Hours @23:20 ("plain React SPA in TypeScript on Vite, FastAPI") and @70:19 ("use a template so we know we have the proper setup… Tailwind and shadcn") · Thomas Hass — How To Vibe-Code Databricks Apps @2:22 (APX = shadcn + Tailwind + FastAPI; "avoid starting from scratch")

So: adopt shadcn/ui vendored into frontend/src/components/ui on Tailwind v4, keep FastAPI serving the SPA. Ebbelaar also pins dependencies with a 7-day minimum release age — worth copying into .npmrc.

2 · Chat table stakes are specific and small

"Enter should directly hit send… Shift-Enter for a new line. Entering a new message should automatically scroll to the bottom… stream responses to the UI — it feels a lot faster because the output is streamed word by word."

Jason Ku (Meta) — A Meta Engineer's Agentic Engineering Workflow @3:16–5:21, @10:08 (typing-dots spinner "matches what most people are used to") · Dave Ebbelaar — 4 Hours @152:13 ("sidebar with the conversations… hide it, open it… what does the chat interaction look like with all of the citations and the loop while users are waiting")

So: rubric criterion 3. Both options: Enter/Shift-Enter, stick-to-bottom with a "jump to latest" pill, per-stage streaming, a collapsible conversation list.

3 · Evidence opens in place, next to the answer

"When you click on the inline citations it opens a new browser tab. Can you make sure clicking an inline citation opens the right citation on the right bar? … show the neighbouring chunks around it to give a little bit more context."

Dave Ebbelaar — 4 Hours @171:02–173:19; @12:06 ("we always want to reference sources so we can backtrack and fact-check") · Apoorva Joshi (MongoDB) — AI System Design: From Idea to Production @17:25–18:38 ("how does the system explain itself? … by providing citations")

So: the retrieved cells light up in the filing itself; the stage trace opens beside the answer, never in a new tab. This is where ConvFinQA can beat generic chat UIs — the evidence is a table, and tables can be highlighted.

4 · Consistency comes from tokens, not from prompts

"Instead of padding 16 pixels and this specific hex number, the design token would be spacing-medium and brand-primary… once you fix one thing, it affects the entire thing. The fix is applied everywhere."

Ras Mic — Building beautiful UI using AI (My design workflow) @0:55 (the dashboard "looks nothing like the homepage"), @1:56, @18:57–21:05 · These UI libraries + AI @10:35–11:31 ("extract the design system from this component… if AI is your foundation it becomes a problem") · Chris Raroque — How I Make Apps FEEL Premium @12:05 ("AI's first output is the starting line, not the finish line… premium is felt more than seen")

So: two-layer tokens with a pre-paint theme script — exactly what data-qa-agent/frontend/src/styles.css does. The redesign ships a token file first and components second.

5 · A demo has to show the system, not the happy path

"It looked great as a demo, leadership would get happy, they would sign it off… after a few weeks people would start asking 'what the hell is AI doing?' … the observability gap, the evaluation gap, the governance gap."

Sandipan Bhaumik (Databricks, AI Engineer) — The Production AI Playbook @2:22–3:30; @15:50 (tracing data "served to auditors, to regulators, to online monitoring") · Kamelia Aryafar — Scalable GenAI in Production @10:04 ("demos are the happy path"), @11:01 ("latency is a product decision, not an engineering one"), @23:48 ("stop building demos… start building systems")

So: traces and production metrics are landing-page content, not admin-only. The demo's job is to make the observability, evaluation and governance answers visible in the first screen.

6 · Show the data behind every score

"I have these five metrics and now for every data point I have this nice dashboard with five scores… but the reality is that you as an engineer have no idea of the data that's flowing through your system. That is a big red flag."

Dave Ebbelaar — How to Systematically Setup LLM Evals @30:49; @31:55 (compare prompts and models side by side); @39:13 ("track everything in Langfuse… then look at those traces") · Elizabeth (Arize) — LLM-as-a-Judge 101 @36:35 (Phoenix)

So: rubric criterion 5. Every metric tile links to its rows; the never-seen vs overall distinction stays in the type, not a footnote; flips (pass→fail) are a first-class list.

7 · The production metrics that matter

"What's your system's average token cost, token usage, average number of turns in a conversation… once accuracy looks good, cost, latency, and reliability become absolutely non-negotiable as you move to production."

Apoorva Joshi (MongoDB) — @23:41–24:52 · Randall Hunt (Caylent) — POC to PROD @15:01 ("speed matters, but UX matters more"; a metric "can just be a boolean — was this inference successful or not")

So: the production panel is p50/p95 latency, cost per turn, tokens per turn, error rate and correct-vs-gold — with the source of each number printed under it. In the demo, replayed timing is recorded-in-dev timing and says so.

8 · The reviewer's twenty seconds

"A success rate of 95% is very intuitive; an F1 score of 39 is perhaps not… if you have done a good job in those first seven — or now even twenty — seconds… make it as easy as possible."

Boris Meinardus — This Simple RESUME got me 5 ML Interviews @4:27–5:33 · Marina Wyss — How to Get Your First AI Engineering Job @7:49–8:41 ("end-to-end… some kind of user interface with relevant monitoring and logging… ideally make some kind of interactive UI") · Stefan Masnikovic — @5:46 ("your portfolio is the technical proof")

So: rubric criteria 1 and 9. One intuitive number first (77.7% on questions no optimiser saw), then the movement (a replayed answer), then the depth. The debrief must read without opening the repo.

What the corpus does not say

Zero relevant hits for Streamlit, Gradio or Chainlit as a demo UI (Streamlit appears only inside Databricks Apps), for Next.js as the frontend of an AI app, for CopilotKit / assistant-ui, for Recharts / d3, or for Braintrust / Logfire. The observability names that do appear are Langfuse (Ebbelaar) and Arize Phoenix. Read that as: the engineers in this corpus ship plain React + Vite + shadcn and point at an external trace tool — this app keeps its in-app trace store and links out to Logfire, which is a stronger position, not a weaker one.

What the two sibling frontends already solved

Surveyed in full: data-qa-agent/frontend ("Data Pilot": React 19, Vite 6, Tailwind v4, shadcn/ui, radix-ui, TanStack Query, react-router 7, visx, cmdk, lucide, Playwright + axe) and transcript-rag-agent/frontend ("transcript·lab": React 19, Vite 7, three runtime dependencies, hand-rolled CSS variables, hash routing, Vitest).

Read the comparison honestly — four caveats the debrief prints beside the table

Different questions. The paper scores the 434-conversation test set, whose gold answers were never released; our 200 conversations are sampled from the public train/dev files, so the two sets do not overlap and are not the same difficulty draw. Different tolerance. The paper's execution accuracy is an exact match on the executed program; ours is a numeric match with rounding tolerance (numeric_match), which is slightly kinder. Different era. A 2026 hosted LLM in a four-agent pipeline with no fine-tuning versus a 2022 fine-tuned RoBERTa pipeline — the comparison shows what the paradigm shift bought, not that this codebase beats FinQANet on its own terms. Program accuracy is not scored here yet. Every turn's pred_program is captured; scoring it against the gold program (normalising argument order and constants) is a small Phase 1 addition and gives the second column.

What gets built, now that the line is drawn

  1. /metrics/production (serving/routes/metrics.py, ~120 lines with tests): aggregates the trace store, grouped by source so live and replayed turns never blend — turns, p50/p95 latency, tokens and cost per turn (tracking/cost.py, which already computes it and is read by nothing), accuracy against gold where gold exists, and error counts by code. This is the endpoint behind the landing tiles, the sparklines and the admin overview.
  2. Latency and tokens where they are missing: they are recorded for live turns and empty in every committed artefact, so the demo would show zeros. Phase 1 persists them into the *_io columns and the demo pack, and re-records the eight filings so a visitor sees real measured numbers with a "recorded in dev" source line.
  3. Error codes, classified (llm_unavailable, not_available_demo, no_recording, rate-limited): today error is free text, so an error-rate tile can count but not explain. One enum, written at the two places errors are caught.
  4. Traces page in the rail, keeping its name: the turns list with filters (source, correct, error, session), the per-turn stage detail already in the inspector, and deep links at /admin/traces/:id. No Spans tab, no Service tab.
  5. Logfire stays where it is: configured, constructing spans, exporting nothing without a token. Set LOGFIRE_TOKEN in a dev shell and the full model-call and request tree appears in Logfire immediately — that is the whole recovery path, and it costs nothing to keep open.
What you give up, stated plainly

A visitor to the public demo will see what the system did — every turn, every stage, every tool call, its latency, cost and correctness — but not what each model request did: no per-call latency histogram, no retry counts, no cache-hit rate, no HTTP route or rate-limiter view. For the demo's purpose that is a fair trade: the trace store already carries the per-stage tool trajectory, which is the part a reader actually wants to inspect. It becomes the wrong trade the day this serves real traffic and someone has to answer "why was that turn slow" — at which point the span processor is a day's work on an interface that already exists in process.

Net effect on the plan: Phase 1 drops from 2 days to 1.5 and loses tracking/spans.py, the spans table and /spans; Phase 4 drops from 3 days to 2.5 and ships Traces rather than a three-tab Observability page; Phase 6 drops /spans from the smoke script. Total: 12.5 days.

11 · Risks & open questions

What could go wrong, and what I could not decide for you

Risks

  • Tailwind 3→4 touches every className. Mechanical, but wide; do it surface-by-surface behind the router as data-qa-agent did, deleting the old block in the same PR that converts a page.
  • Replay timing can mislead. A recorded 6.7 s replayed in 2 s is not "2 s latency". Every production figure in the demo carries a "recorded in dev" source line; the trace store tags replayed turns source="demo" and the metrics endpoint groups by source.
  • Bundle size. shadcn + radix + TanStack + Recharts adds roughly 150–250 KB gzipped; lazy-load the admin pages so the landing stays under 200 KB.
  • The champion / prompts mismatch in /healthz would put the wrong version on the landing page if left as is.
  • Stale chunks after deploy break lazy routes for open tabs — the vite:preloadError reload guard is a documented production incident in the sibling repo.
  • React 18 → 19 is not required for anything here; staying on 18 removes a migration from the critical path.

Open questions

  1. Should first-time visitors see seeded example conversations in their list, or only what they have asked? The mocks assume seeded examples, labelled "recorded".
  2. Should /healthz report the champion's bundle rather than the newest prompt file? I believe yes; it changes what the landing page prints.
  3. Charts: Recharts (fast to build) or lift data-qa-agent's visx components (consistent portfolio look)? The plan assumes Recharts.
  4. Is the ⌘K palette worth a dependency for a demo, or does it belong in a later pass?
  5. Program accuracy: score with the paper's normalisation (argument order, constants) or a stricter exact match? The benchmark table needs one; the plan assumes the paper's.
  6. The paper's "hybrid second part" slice needs the boundary between the two source FinQA questions per conversation; if the public dataset does not carry it, that row stays "—".
