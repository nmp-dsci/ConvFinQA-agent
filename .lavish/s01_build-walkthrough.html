01 · Architecture

What changed, in one picture

The four-stage agent pipeline is unchanged — it was already good. What is new is everything around it: one choke point every model call passes through, a trace of every turn, a registry that decides what may become champion, and a public demo that runs the same build with no keys in it.

03 · The thing you asked for

Making a new model version

A “model version” here is a bundle, not a checkpoint: prompts + GEPA overlay + both model ids + dataset hash + code SHA, versioned together. Three routes produce one, and all three converge on the same evaluation and the same gate.

Walk-through: shipping v4

1

Produce the bundle

Pick whichever route fits. Auto-research and GEPA can both be launched from the Research tab in dev, or from the terminal:

# Route A — hand-edit: create src/convfinqa/prompts/v4.py with the four constants
#            (TRIAGE_PROMPT, PREPROCESS_PROMPT, RETRIEVER_PROMPT, CALCULATOR_PROMPT)

# Route B — auto-research: diagnose failures, propose fixes, keep only what verifies
uv run convfinqa-diagnose --version v2 --variant v4 --limit 20

# Route C — GEPA
RUN_GEPA=1 GEPA_MODE=real uv run convfinqa-optimize

Route B writes prompts/v4.py for you from the rule stores — that module is generated, never hand-edited. To change it, change the JSONL or re-run the harness.

2

Evaluate it

PROMPTS_VERSION=v4 uv run convfinqa-eval

This writes evaluation/predictions/pydantic_predictions_v4.csv, and opens an MLflow run and registers the bundle — because the logging lives inside the runner, not beside it. There is no separate “remember to log it” step to forget.

3

See what actually changed

uv run convfinqa-mlflow compare v2 v4

Or open Experiments → Compare two versions in the app, which shows the same thing with both flip lists side by side. Read the pass → fail column first: that is the one that blocks a promotion, and it names the exact questions.

4

Promote — if it earns it

uv run convfinqa-mlflow promote v4

Exits non-zero and changes nothing if the comparator refuses. In the app it is the Promote button in the registry table, owner-token gated, and it returns 409 with the reason rather than a silent no-op. A refusal is the gate working; the bundle stays registered as a challenger with all its evidence.

5

Ship it

uv run convfinqa-mlflow snapshot   # export history for the demo image
uv run convfinqa-demo-pack         # re-record the demo from the new champion
git add evaluation/ src/convfinqa/prompts/ src/convfinqa/serving/demo_pack/
git commit -m "v4: …"  &&  git push

CI re-scores the committed CSVs, the eval gate enforces the new floor, and merging to main deploys the demo. The prediction CSVs are committed deliberately: they are the reproducibility cache that lets all of this run with zero API calls.

The one trap

Regenerate the demo pack after a promotion, or the public demo keeps replaying the old champion's answers while the registry claims a new one. convfinqa-demo-pack defaults to the registered champion, so running it with no arguments is correct.

04 · The gate

The promotion contract

This is the understanding you confirmed, with the one refinement I raised: “beats the champion” alone is not sufficient.

Condition 1 — accuracy

Candidate accuracy ≥ champion, measured over the questions both runs actually cover.

Condition 2 — no pass → fail flips

Not one question that used to be right may become wrong. This is the load-bearing half.

Why the second condition exists: a change that fixes twelve number-retrieval turns and breaks nine program turns nets out positive. An accuracy-only gate calls that an improvement. It is not — a capability that used to work no longer does, and the headline number hides it. The comparison is per-question precisely so the flip list can be the evidence, and the CI gate prints the questions that broke.

What the registry keeps

  • Every version, forever. Registration captures the full spec; nothing is deleted. A failed challenger keeps its bundle and its eval artifacts exactly as long as a champion does.
  • Promotion is an append-only event — timestamp, actor, comparator verdict, and the runs it was based on. The history view shows the whole chain; nothing is overwritten.
  • How a bundle came to exist is recorded (manual / gepa / s7), so “auto-research produced this one” is a field, not folklore.
  • A forced promotion is recorded as forced. The override exists for a deliberate rollback, and never happens silently.

History is already populated

Backfill reconstructed everything that predates the tracking layer from git — the v1, v2 and v3_1 evaluations, both committed GEPA runs, and both s7 rounds. From here it is captured automatically. Note the champion was seeded by accuracy, not recency:

05 · Shipping

Demo mode & deploying

What makes the demo honest

It replays rather than fakes. Recordings were reconstructed from the committed prediction CSVs — every row already carried the full per-stage IO — so building the pack cost zero API calls. Replay emits the same SSE events the live path emits, paced so a real 30–60 second turn plays in about four seconds. The frontend cannot tell the difference, because from its side there is none.

Below the fuzzy-match threshold it declines rather than serving the nearest recording: 

$ curl -X POST …/ask -d '{"question":"who is the chief executive officer"}'
HTTP 404
{"detail":{"code":"no_recording","message":"This demo replays recorded
 conversations and has no recording for that question. Pick one of the
 suggested questions for this report to see the agent work end to end."}}

Confidently returning another filing's number would be the worst failure a system whose entire subject is numerical accuracy could have. Declining is the feature.

DEMO_MODE is baked into the image, not set in Terraform — so no infrastructure change or console edit can turn the public URL into a billable one, and there is no key in the environment for it to use even if it could.

The ship path

# locally, exactly what ships:
docker compose up demo
./scripts/demo_smoke.sh http://localhost:8080

# then: push → CI must pass → deploy-aws.yml → ECR → App Runner → smoke gate

Six CI gates block every PR: ruff + format + mypy, pytest, the offline eval-regression gate, frontend typecheck + tests + build, a Docker build, and terraform fmt/validate. The deploy workflow is chained on CI via workflow_run and refuses to run unless it succeeded — one deliberate improvement over the sibling projects, whose deploy fires on push regardless, so a red main can ship there.

Infrastructure is ECR + App Runner + a 5xx alarm. No VPC, no database, no Secrets Manager. Measured 225 MiB RSS at rest and 315 MiB with every prediction CSV cached, so the 1 GB instance is the honest floor — 512 MB would boot fine and then OOM the first time someone opened the answers tab.

06 · Worth knowing

Three corrections

Each of these changes something you previously believed to be true, so none of them should stay buried in a commit message.

1. The 770-question set was never held out

The plan and README claimed “77.1% on a 770-question held-out set”. GEPA trained on 120 of the 200 scored conversations, so 461 of those 770 questions were seen by the optimizer. Worse, two different 60/40 “train” splits existed with the same seed but different shuffles, agreeing on only 78 of 120 conversations — and GEPA used the one the serving layer was not reading.

Now: the split lives in data.loader.optimizer_split(), the splits are named optimizer_train / never_seen, and held-out accuracy is reported alongside — never blended into — the overall figure. The good news: the improvement survives and is slightly larger than claimed — +4.9 pp on never-seen data versus +4.2 pp overall. The v3_1 regression is correspondingly larger. Both numbers now appear on the landing page rather than the flattering one.

2. mypy was checking almost nothing

packages = ["src"] pointed at a directory that is not a package, so every convfinqa.* import fell through ignore_missing_imports and resolved to Any — the strict settings applied to hardly anything. Fixing the config surfaced 31 real findings, several substantive: a function advertising it accepted a sync transport for an async client that could never use one, and three FixAttempt | None dereferences in the s7 harness that were safe only by accident. All fixed; the gate is on.

3. Two crashes and a timing side-channel

  • numeric_match crashed on a missing prediction: it arrives as the string "nan", which parses cleanly as a float and then raises inside round(). Found by the new gate re-scoring committed CSVs.
  • The container returned 500 on a read-only route because backends.dspy built its models at import time, so merely reading a dataset fact demanded an API key. A test now pins that every module imports keyless.
  • The review gate caught a genuine one I introduced: the owner-token check used != rather than a constant-time compare — a timing side-channel on the only auth gate protecting promotion and research launches. Now secrets.compare_digest.
