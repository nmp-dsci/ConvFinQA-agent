Can a Haiku 5.5 challenger hold the champion's line for a fraction of the price?

Champion: sdk_v1 · claude-sonnet-5 · effort high, made the universal champion. It beat v8 by +8.9pp (p = 0.0003), and its 90.5% on test100 is the bar. Challenger: sdk_v1 · claude-haiku-5-5 · effort high. The prompt, tools, effort, questions and scorer are all the same, and only the model differs. Score the challenger on exactly the test and train questions sdk_v1 already ran on, pair it against those committed runs, and promote it only if it beats or matches the champion under a rule fixed before any Haiku 5.5 number exists. That's three Haiku passes on the subscription, about 45 minutes. Sonnet is never re-run, and nothing goes to the API.

01 · where we are

Today the champion is a prompt, and the model is a setting. A challenger needs both in one record.

Serving runs sdk_champion (sdk_v1 · s1 · 5e96f2bf) in one Agent SDK session per conversation, with the six calculator tools only. The model comes from settings.sdk_model (config.py:96) and effort is hard-coded. The registry also still has champion = v8. The challenger shares the champion's prompt hash, so as a prompt version it can't even be told apart from the champion. That is why §05 makes the champion an agent configuration: (prompt, model, effort).

The 90.5% was measured at effort=high, not low. Every committed SDK eval run (2026-09-05/06) predates commit 27e11b5 (2026-09-10), which pinned effort="low". Before that pin, effort was unset, and per the commit, ClaudeAgentOptions then defaults to "high". So Haiku 5.5 at high against the committed Sonnet run is like for like. It also means serving has run Sonnet 5 at low since 09-10, which is not the configuration that won and has never been scored. Making the champion record carry effort: high puts serving back on the measured configuration.

Program turns −5.0pp (4 fixed / 16 broken, p = 0.017 toward worse). The loss came from multi-step planning, not from looking values up. That slice is where Haiku 5.5 has to hold.

Why the cost estimate is a range. Haiku 4.5 ran $17.14 at $1 / $5, with no thinking. Haiku 5.5 is 10× cheaper per token than that, but it counts about 30% more tokens for the same text. At effort=high it also thinks, and thinking is billed as output. Estimate ≈ $2–6 per 349-question pass, against $27.62 for Sonnet (also at high), so roughly 5–14× cheaper. Phase 0 measures this figure before anything depends on it.

One difference can't be removed: the tokenizer. The 60k ceiling counts new input and output tokens, and thinking is output. Haiku 5.5 counts more tokens for the same text, and at effort=high it thinks. Sonnet at high stayed under the ceiling on all 349 questions, but a conversation that fits under Sonnet could still hit it under Haiku, and its remaining turns would be recorded as errors. That would charge a harness limit to the model. Phase 4 counts ceiling hits per arm. If they differ, the result is reported as confounded, not as a verdict.

03 · the decision rule, fixed before the runs

Three outcomes, written down first

On test, Δ = Haiku 5.5 − Sonnet 5 on the 349 paired questions, computed with the gate's own statistics: the cluster-corrected McNemar test (Durkalski, clustered by conversation) and the cluster bootstrap CI, from tracking/comparator.py. On train both arms stop at the first wrong answer, so later turns have no counterpart. The paired unit there is the conversation: answered right to the end, or not. "Beats" is the existing improvement gate. "Matches" is new: a non-inferiority promotion, which only makes sense because the challenger is cheaper. The verdict is appended to gates.jsonl as a new kind (a trailing column with a default, as the ledger rules allow), so the promotion has a ledger row behind it like every other one.

beats promote challenger

  1. Test: Δ > 0 and one-sided cluster p < 0.05.
  2. Train doesn't contradict it (rule 4 of "matches").

The house gate's own rule, so "beats" means what it means everywhere else in this repo.

matches promote challenger

  1. Test: the 95% CI lower bound ≥ −3pp (δ, decided in D1).
  2. Test is not significantly worse (one-sided cluster p toward worse ≥ 0.05).
  3. Program turns on test are not significantly worse. This is the slice Haiku 4.5 failed on.
  4. Train replication: across both sdk_v1 draws, the conversations Haiku answers right to the end are not significantly fewer than Sonnet's 64 + 68 of 200 (exact one-sided McNemar on conversations, p toward worse ≥ 0.05).
  5. Every pass complete: zero unscored rows, and no token-ceiling errors (Sonnet had none).

falls short champion holds

  1. Anything else. The row still lands in the model-swap table, because a measured "no" is a result.

Next levers are outside this plan: Haiku 5.5 at xhigh, or a prompt campaign run on Haiku.

The run name gets a slug (…-haiku-5-5-high-…), and --resume-from refuses a mismatched effort. The teacher and judge keep their own low in teacher_options. Runs with no sdk_effort param that predate 27e11b5 read as high.

Today story.sdk_model_comparison pairs sdk-evalloop-test100-* runs only and groups them by model. Extend it:

  • Group by (model, effort), so a later Haiku run at another effort never collapses into this one.
  • Add a train pair that matches runs on train_draw_seed (2027 with 2027, 2028 with 2028) and requires stop_at_first_wrong on both sides. Its unit is the conversation: answered right to the end, and the turn of the first error. It uses an exact paired McNemar on conversations, because with early stop a question-level pairing would be biased toward whichever arm stopped later.
  • Add a verdict: beats · matches · falls_short from §03, with δ held in a named constant pinned by a test.
  • Tests: draws paired only by seed, a mismatched stop flag refused, verdict boundary cases. agent-sdk.html and /optimise/runtimes gain the train column, and story_check covers it.

05 · the universal champion

One champion, and it is an agent, not a prompt

Today the registry holds champion = v8 and sdk_champion = sdk_v1. Guards keep them apart: registry.promote refuses sdk versions and set_alias refuses a cross-runtime pair, because serving built four agents from champion. The workstream below collapses them into one record, so that "promote the Haiku challenger" is a single, recorded registry write.
