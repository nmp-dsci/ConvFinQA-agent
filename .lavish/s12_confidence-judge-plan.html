s12 · plan · confidence judge & selective answering · branch guide-rail · 2026-09-07

Answer when a judge can verify the trace; abstain when it cannot

The runtime decision is made: one Claude Agent SDK session, sdk_v1, scores 90.54% on the 349-question gate. This plan adds the piece that makes that shippable — a second, cheap model that reads the session's own evidence (retrieved cells, program, calculator calls, answer) and scores how likely the answer is right, so production returns only the answers it can stand behind and routes the rest to a person.

Decided: the design is an LLM-as-judge trained on the evals — Claude Haiku 4.5 reads the trace, Sonnet 5 stays the answering agent. This page sizes the training data (50/50 for tuning, natural mix for calibration), fixes what "trained" means in MLflow, and keeps a fitted-calibrator fallback in reserve. Every open decision was settled in review; §09 lists them. It starts from three measurements taken today on data already on disk, one of which changes the shape of the problem.

01 · Goal and the shipped behaviour

Today the SDK runtime returns every answer with equal conviction, and one in ten is wrong. Desired: every turn carries a confidence score from a judge that never saw the gold answer; a threshold splits it into two bands; the high band goes to the user, the low band becomes "I'm not confident in this one". A human-review queue is deliberately out of scope for this phase — the low-band turn is still recorded with its verdict, so the queue is a later read of data this phase already writes. The judge sees the same thing a reviewer would — the question, the document, and the session's trajectory — and nothing else.

02 · What the data already says

Three things were measured this morning from committed CSVs and .traces/traces.db, no model calls. They set the floor the judge has to beat and the ceiling it cannot exceed.

A second model re-solving is not enough

24 / 322
agreed-and-wrong on the gate
Haiku's answer matches Sonnet's on 322 of 349 turns; 24 of those matches are both wrong

If "two models agree" were the confidence signal, the high band would be 92.5% accurate and would catch only 27% of the failures. The two models share their mistakes — same table misread, same period slip — so agreement mostly confirms the error. Whatever the judge does, it has to check the evidence, not vote.

Cheap trace signals do not carry it either

3 / 99
failures any structural flag catches
over 967 Sonnet sdk_v1 turns: skipped stage, inline arithmetic, no tool call, turn cap, missing source

The session almost never fails visibly: 19 flags fire in 967 turns and only 3 of them sit on a wrong answer. The failures are well-formed trajectories with a wrong value or a wrong operation inside them — which is exactly what a reading judge can see and a rule cannot.

The solution: the judge reads the trajectory against the document and tests six claims per turn — is the cited cell the one the question names, is it the right period, does "that" resolve to the right prior turn, does the program do what the question asks, do the tool calls compute it, does the unit match. Those checks are the judge's output schema (§04), and the failure ledger says they cover the misses.

Some failures are not the agent's

~4–7%
of wrong turns where gold is suspect or ambiguous
2 of 56 diagnosed sdk_v1 misses are gold-answer-contradicts-gold-program; project-wide the NON_AGENT share is ~7%

A judge that reads the evidence will — correctly — call those answers right. They land in the high band as "errors" and no judge can move them. The target in §03 is stated against attributable failures for that reason, and the dataset build excludes NON_AGENT verdicts from the negatives.

What the misses look like. The 56 diagnosed sdk_v1 first-wrong turns are dominated by checkable things: calculator/wrong-format (13 — the number is right, the unit or scale is not), triage/wrong-turn-type (9 — computed when it should have looked up, or vice versa), preprocess/wrong-operation (6), retriever/wrong-period (6), retriever/wrong-value (3). Each is a specific claim about the trace that a judge with the document in front of it can test: is the cited cell the one the question names? is that the period asked for? does the program do what the question says? does the answer's unit match? That is the judge's checklist, and it comes straight from the diagnosis ledger.

03 · The honest target

The brief is "the high band is 100% accurate and the low band holds 100% of the failures". Nothing finite proves 100%; what an evaluation proves is an upper bound on the error you did not see. With zero misses in n trials, the 95% bound on the true miss rate is ≈ 3/n (the rule of three). That converts the brief into numbers you can size a dataset against:

Claim you want to makeZero misses needed among…Where that many come from
High band error ≤ 1% (95% conf.)300 high-band answersthe gate split alone (349 turns, ~90% answered)
High band error ≤ 0.5%600 high-band answersgate + one confirmatory draw
High band error ≤ 0.3%1,000 high-band answersgate + two confirmatory draws
Failure capture ≥ 90% (miss ≤ 10%)30 wrong answers, all caughtthe gate split alone (33 wrong)
Failure capture ≥ 95%60 wrong answers, all caughtgate + one confirmatory draw
Failure capture ≥ 97%100 wrong answers, all caughtgate + two confirmatory draws

Two consequences. Negatives are the scarce resource: at a 10% error rate every 100 wrong answers costs 1,000 scored turns, so the volume plan in §05 is driven by how many failures you need, not how many questions. And the operating point is a choice, not an output — the judge produces a curve (coverage against error, "risk–coverage"), and the threshold τ picks a point on it. Tightening the error bound always lowers coverage, i.e. sends more turns to the human. Decision D2 below sets the point.

Recommended operating point: high-band error ≤ 1%, maximise coverage subject to that; report failure capture beside it.

Provable on the gate split with the data you already have, and it beats the paper's human expert (89.44%) by construction: the answered subset is ≥ 99% correct. Coverage is the number to watch — if the judge can only hold 1% error by answering 60% of turns, the feature is a triage tool, not a product; if it holds it at 85%+, it ships.

04 · The judge — decided design, and its fallback

Decided: Option A. Sonnet 5 keeps answering; Haiku 4.5 judges. Option B stays on the page as the fallback it turns into if A's calibration fails, because A records everything B needs. Both read the same input — the question, its history, the report's text and table, and the session's capture (sub-questions, retrieved values with their cited sources, program, calculator trajectory, answer, the agent's own reasoning) — and both hide the gold answer. They differ in what the model is asked to emit and what "training" means.

decided one call per turn Haiku 4.5 judge · Sonnet 5 agent

Option A · LLM-as-judge, trained on the evals

score = judge's own probability
Emits
A structured verdict: a checklist of named checks (operand-in-source, period-matches, reference-resolved, program-matches-question, arithmetic-verified, unit-and-scale) each pass / fail / cannot-tell, then a binary band: high | low (high = correct, answer it; low = incorrect, abstain), a p_correct kept for the curve, and a one-line reason.
Score
The band is the contract; p_correct is recorded so the risk–coverage curve and a τ can still be read off the calibrate split if the binary verdict proves too coarse.
Training
Diagnose, then distil — the same two moves that produced sdk_v1. A diagnose agent that does see gold goes through every case, correct and incorrect, and writes what the trace got wrong or what it got right; a distil pass reads all of those diagnoses and writes the judge's system prompt, which sees no gold. Iteration re-diagnoses the judge's misses and re-distils. Details below. Lineage judges in registry.json, versions j1, j2, …, alias judge_champion.
Cost
~5k input / ~400 output tokens → ≈ $0.007 per turn on Haiku 4.5. Latency +2–4 s, in parallel with rendering.
Catches
Exactly the §02 classes: it re-reads the cited cell, re-checks the period, re-derives the operation from the question. Format errors are near-free for it.
Weak spot
The score is a model's self-report, not a frequency; calibration can drift between judge versions and must be re-fitted each time. Two judge misses that share a cause need the writer to see both — which the ledger gives it.
fallback only k calls per turn

Option B · Check extractor + fitted calibrator

score = logistic model over judge outputs
Emits
Only the checklist — no global probability. Sampled k = 3 times at temperature so each check has a pass-rate, plus the independent-re-solve agreement from §02 as one more feature.
Score
A logistic regression (or isotonic map) fitted on the judge-dev set turns the feature vector into a real calibrated probability. Logged with mlflow.sklearn.log_model, signature and all; τ is a property of the fitted model.
Training
Real supervised training on labels gold already provides. The judge prompt is frozen; what changes between versions is the feature set and the fit. Re-fitting after a judge-model upgrade is a script, not a prompt campaign.
Cost
3× the calls (parallel, so latency similar) → ≈ $0.02 per turn; +~10 s and another SDK-style solve if the re-solve feature is kept.
Catches
The same classes, with a proper reliability curve and a per-check attribution of why the score is low — useful in the human queue.
Weak spot
Needs more negatives to fit than A needs to tune: ~150 wrong turns before the coefficients stop moving. The re-solve feature was measured at 92.5% / 27% on its own; it helps only in combination and costs the most.
How the fallback stays free. Build A with B's structured checklist as the output schema from day one, so every judge run also produces the features B needs. If A's raw p_correct holds the D2 error bound at ≥ 85% coverage on the calibrate split, ship A. If it holds the bound only by abstaining on a third of the turns, or its calibration is visibly off (reliability curve far from the diagonal), fit B's calibrator on the same runs — no new data is required, because the checklist was recorded all along. That ordering costs nothing extra and keeps the decision empirical.

How the judge is trained: diagnose with gold, distil without it

1 · Diagnose — with gold

Teacher model: Sonnet 5 (decided in review; the loop's default teacher is Opus 5, so the judge commands pin claude-sonnet-5 and record it as the diagnoser_model on every ledger row). Per case the teacher receives gold answer + gold program, the agent's answer + program, the retrieved values with sources, the calculator trajectory and the document. For a wrong case it writes the existing taxonomy label, what went wrong, and the evidence in the trace that reveals it. For a right case it writes what it got right — the checks that pass and the trace features that confirm it — and, importantly, whether a judge without gold could have known. Output: judge_diagnoses.jsonl, one row per case, appended never rewritten.

2 · Distil — without gold

One teacher call reads every diagnosis and writes prompts/judge_j1.py: the rules that separate the right traces from the wrong ones, phrased as checks the judge can run on the answer, program and trace alone. The distil prompt forbids any reference to gold — it is validated by a test that the judge prompt contains no gold field names — and the output schema is fixed by JudgeVerdict. Registered by hash in registry.json → judges.

3 · Score, then iterate

Haiku runs j1 over the calibrate split (natural mix). Misses — wrong answers banded high, right answers banded low — go back through step 1 with the judge's own reason attached, and step 2 writes j2. The gate promotes judge_champion only if coverage rises at the target error bound and failure capture does not fall; cap five versions. The gate split is scored once, by the frozen champion.

The judge's output schema

class JudgeVerdict(BaseModel):
    checks: dict[Check, Literal["pass", "fail", "cannot_tell"]]
    #   operand_in_source   – every retrieved value is in the cited cell / sentence
    #   period_matches      – the period of each operand is the one the question names
    #   reference_resolved  – "that", "this change", "the sum" bind to the right prior turn
    #   program_matches     – the operation(s) are what the question asks for
    #   arithmetic_verified – the tool calls compute that program and the answer is the result
    #   unit_and_scale      – %, millions, sign, rounding match the question's framing
    band: Literal["high", "low"]   # high = correct, answer; low = incorrect, abstain to a human
    p_correct: float          # recorded for the risk–coverage curve; Option B's calibrator reads the checks
    reason: str               # one line, shown in the review queue
    # never present: gold_answer, gold_program — the judge is not told them

Should the training data be sampled 50/50 correct / incorrect?

Yes for the set the judge is tuned on; no for the sets that pick the threshold and prove the claim. The two jobs want different mixes, and using one mix for both is the classic way a judge ends up abstaining on a third of production traffic.

SplitMixWhyTurns
judge-optimise — what the prompt writer sees~50 / 50: every attributable negative, plus an equal number of positivesThe writer's unit is a miss; at natural prevalence 9 of 10 cases it reads are correct answers and the misses drown. Balancing makes each experiment's evidence dense. Positives are not random: pick the hard ones — the 16 turns where a structural flag fired and the answer was still right, the 18 where Haiku disagreed and Sonnet was right, and a stratified fill by turn type and conversation type — so the judge learns not to over-abstain on unusual-looking but correct traces.~72 now (36 + 36) · ~200 with draws
judge-calibrate — picks τ, gates versionsnatural (~10% wrong)τ, coverage and high-band precision are all prevalence-dependent. A threshold chosen on 50/50 data assumes half the traffic is wrong and sends far too much to the human; a precision measured there means nothing in production. Never rebalance.~300 now · ~630 with draws
judge-test — the gate, oncenaturalSame reason, and it is the split the runtime's 90.54% is stated on, so the selective figure sits beside it like-for-like.349

The consequence for volume: the negatives are what you pay for. At 90% accuracy every scored turn yields 0.1 negatives, so the question "how many turns?" is really "how many failures do I want the judge to have seen?":

Every draw also yields ~90 positives, so the 50/50 optimise set never lacks its other half; the natural-mix calibrate split is simply the remaining 40% of the draws untouched. One caution on "trained on the evals": the judge must be tuned on the agent's failures under the prompt that will serve — sdk_v1 on Sonnet — not on the pipeline's or Haiku's. Those other passes are a robustness check, never training data.

Rule of thumb for the volume: a judge needs ~100 negatives to tune against and ~60 untouched negatives to prove a 95%-capture claim. At this runtime's 10% error rate that is ~1,600 scored turns for development and the gate for proof — five 100-conversation draws in total, three of which do not exist yet. Also worth having, not for the production judge but for its robustness check: the sdk_v2 and Haiku passes on the gate (43 and 44 wrong) are a free out-of-distribution set — a judge that only works on Sonnet's failure style will show it there.

06 · Training and tracking in MLflow

The judge follows the pattern every other artefact in this project follows: a lineage in registry.json, an alias that serving reads, runs the runner logs itself, an append-only ledger, and a promotion rule enforced in code.

Experiment convfinqa-judge

One run per (judge version × dataset split). Params: judge_model, judge_version and prompt hash, runtime_version (sdk_v1) and its model, dataset hash and split, k samples, threshold, error_target. Tags mirror the params that are search keys — same convention as sdk_model.

Metrics per run

auroc, aurc (area under risk–coverage), coverage_at_target, selective_accuracy_at_target, failure_capture_at_target, brier, ece, plus the same by gold_turn_type. The gate's own conversation-clustered bootstrap gives CIs; the dashboard number is coverage at the bound.

Artefacts per run

judge_scores.csv (one row per turn: score, checks, band, correct), risk_coverage.json and its plot, reliability.json, flips.json for judge-vs-judge comparisons (which turns moved band), the fitted calibrator as an MLflow model for Option B, and the judge prompt by reference through prompt_refs — never raw text.

Promotion rule for judge_champion

On the calibrate split, with τ set to the D2 bound: coverage rises, failure capture does not fall, and the clustered one-sided test on the band decisions clears α — the same shape as the runtime's rule. Refuses train evidence, refuses any run whose runtime_version is not the current sdk_champion: a judge is calibrated to one agent, and swapping the agent silently invalidates it.

Tracing in production

The judge is one more Agent-SDK-style call outside the autologger's reach, so it gets a hand-opened LLM span the way evalloop/sdk.py::run_structured does — inputs by reference (judge_prompt, the capture's trace id), outputs the verdict, attributes for model, tokens, cost and band. In serving it nests under the session's turn span so a reviewer opening the queue item sees the whole story in one trace. The ledger row (judgements.jsonl, append-only, frozen columns) is what backfills and the write-up read.

08 · Risks

  • Correlated blindness. The judge reads the same document the agent did; a table both misparse is invisible to both. §02's 24 agreed-and-wrong turns are the size of this today. Mitigation: the checklist forces the judge to quote the cell, not restate the value; a human queue (out of scope this phase) is the eventual backstop for what survives. This is why the target is a bound, not a promise.
  • Label noise trains the judge to distrust correct answers. ~4–7% of "wrong" turns are gold's fault. Excluding NON_AGENT verdicts from negatives is necessary; it means the judge-dev set depends on the attribution rule and must be rebuilt (with its attribution_rule tag) when that rule changes — the same guard backfill-attribution already uses.
  • Calibration is per agent version. Promote a new sdk_vN and τ is wrong until the judge is re-calibrated on that version's turns. The promotion rule refuses a mismatched runtime_version; the campaign runbook has to say "re-score the judge" as a step after any runtime promotion.
  • Billing path for the judge. The only Anthropic path in llm.py today is the Agent SDK on the subscription; there is no Anthropic API client at all. A Haiku judge in production has to be an API call (serving cannot hold a subscription session), which is new wiring and a new key — and the standing rule that the SDK runtime never bills the API stays untouched. Development can run the judge through the SDK on the subscription to avoid API spend while iterating; D4 decides.
  • The 33 gate negatives cap the proof. With zero misses the miss-rate bound is still ~9%. The confirmatory draws exist for that reason; say so in the write-up rather than round to "100%".
  • Latency and turn budget. +2–4 s per turn for A, more for B with the re-solve. The session's own median is 31 s, so this is small in proportion, but the abstain path must not wait on a second full solve in the user's request — B's re-solve, if kept, runs concurrently with the judge.
  • Abstaining changes the conversation. A later turn may depend on an answer the user was never given. The session still holds it, so the agent stays coherent; the UI has to make clear that the low-band value exists but is unverified, or later turns become confusing.

09 · Decisions

All decisions are made (review of 2026-09-07).
  • Design: Option A — LLM-as-judge trained on the evals, by diagnose (with gold) → distil (without gold) → score → iterate.
  • Models: Sonnet 5 answers · Haiku 4.5 judges · Sonnet 5 is the diagnose/distil teacher (not the loop's default Opus 5).
  • Training data: 50/50 correct/incorrect for the optimise split; natural mix for calibrate and test.
  • Operating point (D2): high-band error ≤ 1%, maximise coverage; failure capture reported beside it.
  • Data budget (D3): no fresh draws yet — start from the 967 turns on disk; draws only if the first curve says they are needed.
  • Judge billing (D4): subscription (Agent SDK, Haiku) while developing; an API path for production serving.
  • Low-band UX (D5): abstain only — no human review queue in this phase; low-band turns are still recorded with their verdict so a queue can be added later.
