s11 · results & runtime decision · branch agent-sdk-experiment · 2026-09-06

One Claude session, carrying everything the DeepSeek campaigns learned, beat the four agents that learned it

The Agent SDK arm answers the same 349 gate questions as the pipeline, through the same evaluator, the same paired significance rule and the same append-only record. It scores 90.54% against the optimised pipeline's 81.66%, and the whole gain sits on the turns that require arithmetic.

A second scoring pass answers the model half of the confound: the same distilled prompt on Claude Haiku 4.5 scores 87.39% — 3.15pp under Sonnet 5 (just short of significance, p = 0.051) and still +5.73pp over the optimised pipeline at p = 0.017. Most of the gain survives a smaller model; the architecture and the distilled knowledge are carrying it.

This is not a from-scratch win, and reading it that way would draw the wrong conclusion. The single prompt that scored 90.54% was written by distilling v8's four tuned prompts — the accumulated output of three campaigns and seven experiments of DeepSeek optimisation — into one document. Every domain rule the pipeline had learned about turn types, reference resolution, table-versus-text retrieval, period alignment, sign conventions and calculator discipline came across. The new architecture then removed what those prompts had been carrying on top: the inter-agent plumbing, the re-rendered history, the stateless hand-offs. So the right reading is that the campaigns produced the knowledge and the single session was a better vessel for it — which is also why pointing the same loop at the distilled prompt could not improve it further.

Move the runtime to agent_sdk.

03 · Where the difference is

The dataset splits every turn into a lookup and a computation. Reporting only the aggregate would describe neither, because the two behave nothing alike: both arms have saturated the lookup, and the entire delta is carried by the reasoning turns.

04 · The two architectures

multi-agent · what runs today

v8deepseek-v4-flashpydantic-ai

Four stateless agents in a fixed Python-controlled order: triage decides the turn type, preprocess writes sub-questions and a symbolic program, the retriever pulls each operand, the calculator executes through six tools. History is re-rendered into a text block on every turn because no agent holds any.

Four prompt lineages, ~22k characters total, each tuned separately across three campaigns. One experiment moves exactly one prompt, so every champion move has a named cause.

agent_sdk · the challenger

sdk_v1claude-sonnet-5claude_agent_sdk

One Claude session per conversation. The report arrives in the first message, each later turn is just the next question, and the session already holds its own prior tool calls and answers. The six calculator functions are its only tools — triage, planning and retrieval are a train of thought it follows and reports, not a pipeline it is pushed through.

One prompt lineage, 16.4k characters. It reports its stages in a structured result, so the same gold-derived panel and the same first-fault attribution apply with no new scoring code.

Nothing forces the trail, and that is measured too.

A program turn that reports no plan is counted as a preprocess skip; one that answers with no calculator call is a calculator skip; an answer matching no tool return is counted as inline arithmetic. Across 349 questions sdk_v1 recorded 3 stage skips and 5 inline-arithmetic answers — small enough to report as a finding rather than a defect, and visible rather than assumed.

05 · Distillation was the peak — and why the loop may never have had a fair shot at beating it

The first SDK prompt was not hand-written, and it was not written from the dataset either. The teacher agent read the pipeline's four already-optimised v8 prompts — every rule three campaigns of DeepSeek experiments had put into them — plus the dataset notes, and distilled them into one document with the train of thought as its spine, dropping the inter-agent plumbing that only exists because the pipeline's agents cannot see each other. That distillation, never itself optimised, is the 90.54%.

So the sequence is: the campaigns learned the domain, the distillation carried it over, and the architecture stopped taxing it. Each step needed the one before.

Then the same loop that produced v8 was pointed at it. One experiment completed:

A likelier explanation than "the prompt is finished": the loop is starving

Before concluding that the distilled prompt cannot be improved, look at how much material the loop actually had to learn from. A train draw is 100 reports, resampled each cycle, early-stopped at the first wrong turn. At the pipeline's accuracy that yields plenty of failures. At 90.5% it does not:

So a draw hands the SDK teacher roughly 34 first-wrong cases. Split four ways that is about eight per stage, and split by failure class — which is what the SDK arm actually ranks on — the top class in s01-e02 was 12 cases out of 33 pooled, and the second and third were 5 and 4. A Wilson lower bound over four or five cases is barely a ranking at all.

This project already documented that exact failure mode on the other arm.

The pipeline hit it first: one draw is about 50 first-wrong cases split four ways, the top two agents sit within a couple of cases, and a single draw's ranking is therefore noise. The fix adopted then was to pool every draw that ran the same prompt. The SDK arm cannot lean on that yet — pooling needs draws, and the cap of 2 means it has two, one of which never reached a rewrite. It is starved on both axes at once: fewer failures per draw, and fewer draws.

The constraint is not the dataset. Excluding the gate split, the pool holds 3,098 drawable reports, so the 100-report draw is a budget choice rather than a ceiling. Raising it scales the learning material about linearly at the measured yield:

reports per drawexpected first-wrong casesper stagewhat it buys
100 (today)~34~8a ranking that is mostly noise
150~51~13parity with what the pipeline's loop had per draw
300~102~26a class-level sample worth ranking on one draw

The cost is real and is why this was not simply done: a draw is qa_agent traffic on the subscription, so tripling the draw roughly triples the wall clock and the rate-limit exposure per cycle — and a throttled cycle is exactly what killed the second experiment. That is a budget decision, not a technical obstacle.

What this means for the conclusion above.

"The loop could not improve the distilled prompt" is what was observed, and it is the honest headline for one rejected experiment. But it is not yet established that the prompt is at its ceiling, because the loop was never given enough failures to rank classes reliably. The two readings — the knowledge is already in the prompt, versus the loop is under-powered — both fit the evidence, and telling them apart is a bigger train draw, not a cleverer teacher.

The interesting result is not that the loop failed — it is what the failure says.

The pipeline needed three campaigns and seven experiments to climb 77.08% → 81.66%. The SDK arm reached 90.54% with a prompt written once — but that prompt is those seven experiments, distilled. The loop's best attempt on top of it then made things worse. Read together, the most defensible reading is that the campaigns bought two different things at once: real domain knowledge, which transferred intact, and compensation for the pipeline's own architecture, which became dead weight the moment the architecture went away. That also explains the failed experiment: with the transferable knowledge already in the prompt and only 33 wrong turns left, some of them suspect gold labels, there is very little for a further edit to find. The lesson is not "skip the optimisation" — without it there is nothing to distil. It is that the optimisation's value outlived the architecture it was tuned for.

06 · The model swap: the same prompt on Sonnet 5 and Haiku 4.5

The cross-runtime result changed the model and the architecture in one step. The half of that confound this project can measure without an API endpoint is the model: run the identical sdk_v1 prompt, the identical six calculator tools, the identical 349-question gate split and the identical scoring, and swap only the model. That was done on 2026-09-06 as a single scoring pass — no optimisation, no campaign, nothing promoted — with Claude Haiku 4.5 (claude-haiku-4-5-20251001) in place of Claude Sonnet 5. The pass completed with zero refusals and zero unscored turns.

What it says. Three things, in order of confidence.

  1. The architecture plus the distilled knowledge carries most of the gain. Haiku on the same prompt still beats the optimised four-agent pipeline by 5.73pp, and that clears the same one-sided clustered rule the campaigns use (p = 0.017, CI entirely above zero). Two thirds of the +8.88pp headline survives a model downgrade.
  2. The model is worth about three points at this prompt, and all of it is reasoning. Number turns are a wash (Haiku 96.40% vs Sonnet 95.50%, +0.9pp, noise); program turns move −5.04pp with 16 broken against 4 fixed, z = −2.12. The aggregate −3.15pp sits at p = 0.051 with the CI just touching zero — read it as "probably real, not proven at α = 0.05 on 349 questions". The per-stage panel points the same way: preprocess (planning) drops 3.4pp and calculator 5.1pp, retrieval barely moves.
  3. Cost is the argument Haiku has left. $17.14 against $27.62 for the same pass — 38% cheaper, for about three points. Whether that trade is worth taking is a serving decision, not an accuracy one.
What this does not settle.

The prompt was distilled from four DeepSeek agents and then scored on both models with no further optimisation, so neither figure is that model's ceiling — a Haiku-targeted campaign might close some of the gap, and no such campaign was run (by instruction: scoring only). And the confound is only half open: the pipeline was never run on Claude, so "one session beats four" is still demonstrated at equal effort rather than isolated. The one-sided p for the Sonnet–Haiku pair is taken in the direction of the observed delta — the gate's own p only looks towards improvement, and a scoring pass has no preferred direction.

How to read the cost and latency rows.

  • Cost bases differ and neither is a bill. The DeepSeek figure is token counts priced at the list rate in tracking/cost.py ($0.28 / $0.42 per million in / out). The SDK figure is the total_cost_usd the SDK reports per turn — the API list price for what the session consumed — while the passes actually ran on the subscription and billed nothing per token. The comparison is like-for-like as a list-price comparison only.
  • The session's cost is almost entirely cache reads. 99.97% of the SDK arm's input tokens are cache hits: the report and every prior turn are re-read on each call. That is the price of the design that removed the pipeline's re-rendered history — the context is paid for on every turn instead of being rebuilt in Python. Fresh input is negligible; output is where the models differ, and Haiku writes 2.6× as many output tokens as Sonnet for the same conversations.
  • Haiku was slower than Sonnet here, and that should not be taken as a property of the model. Per-question median 53 s against 31 s, p90 118 s against 49 s. Two things are in that number that a clean latency benchmark would exclude: the longer outputs above, and whatever subscription throttling the CLI applied during a 100-conversation pass at concurrency 8 on a Saturday morning — the wall clock is 12% longer, the per-turn latency 70% longer, which is the signature of queueing rather than generation. The pipeline's 7 s is four sequential DeepSeek calls with no such contention.
  • The first turn is the expensive one in the session. Turn 0 carries the whole report into context (33 s Sonnet, 55 s Haiku); later turns are the same order because the cache read is re-billed and re-processed each time. The pipeline's turns are flat at 6–9 s because every turn is the same four calls with a re-rendered history block.
  • Throughput at concurrency 8 is a property of this harness, not a ceiling. One subprocess per conversation is the session's unit; the pipeline's is one HTTP call per agent. Neither number says what either runtime does at production concurrency.
What this changes about the decision.

Nothing about the accuracy verdict, and a great deal about what adopting it costs. At list prices the session runtime buys 8.9 points for 23× the spend and 4× the latency on Sonnet, or 5.7 points for 14× the spend on Haiku — with the latency figure clouded by throttling this project cannot control on a subscription. A serving decision has to pick a point on that curve; the eval loop's job was to make the curve measurable, and it now is, per model, from the same record.

07 · What made this measurable

The comparison is the deliverable here, more than either number. Two runtimes that share nothing — different provider, different process model, different control flow — were made comparable because the loop and the tracking store fix everything except the thing under test:

One fixed split

Both arms answer the same 349 questions from the same 100 reports, drawn from a committed manifest. Paired per question, so the test is on the same items and not on two samples.

One evaluator, one panel

The SDK agent reports its stages into the same capture shape the pipeline emits, so the same gold-derived metrics and the same first-fault attribution compute for both — zero new scoring code, zero judge calls.

One significance rule

Net positive and one-sided cluster-corrected McNemar below 0.05, clustered by conversation, with a bootstrap CI on Δ. The rule that rolled back three pipeline versions is the rule this passed.

One append-only record

Three ledgers — diagnoses, rewrites, gates — joined by ids, so any edit traces to the cases that motivated it and the verdict it earned. A crashed cycle wrote no phantom row.

Concretely: --runtime agent_sdk is a flag on run, diagnose, propose, cycle and gate-targeted. Everything after the capture dict is code both arms share. That is why swapping a runtime is a measurable claim here instead of an impression, and why the same harness can judge whatever comes next.

08 · Caveats, stated plainly

90.54% is above the paper's human expert figure, on a public dataset.

Human expert execution accuracy is 89.44%. ConvFinQA is public and any frontier model may have seen it, so contamination cannot be excluded and the absolute number is not a generalisation claim. Two things soften it without settling it: program accuracy is only 0.409, so the agent is not reproducing gold programs, and the paired comparison stays fair because both arms face the same exposure. Our figures are also on a split drawn from the train pool, not the paper's test set.

Model and architecture changed together, and the confound is only half isolated.

The pipeline runs DeepSeek v4-flash; the SDK arm runs Claude Sonnet 5. The model half is now measured within the session runtime (section 06): swapping Sonnet for Haiku on the same prompt costs about three points and still leaves the session +5.73pp over the optimised pipeline. The other half — a four-agent pass on a Claude model — needs an API endpoint, and this project runs the SDK on the subscription only, by decision. So "one agent beats four" is still demonstrated at equal effort rather than isolated; what the swap adds is that the gain is not an artefact of one particular model.

Two smaller ones.

The gate split has now judged around a dozen comparisons, so mild selection pressure exists; the sealed holdout is the only clean confirmatory read left and was deliberately not opened for an experiment. And neither arm is deterministic — the bootstrap CI absorbs that, and every number here is read from a committed CSV rather than a re-run.

09 · What ships next

done in this branch

  • The agent_sdk runtime, one session per conversation, calculator-only tools.
  • Its own diagnosis and teacher agents, and its own prompt lineage sdk_prompts.
  • Three append-only ledgers, backfilled over the pipeline's history.
  • Rate-limit refusals treated as unscored rather than wrong, and --resume-from to finish a throttled pass.
  • The comparison published to docs/optimization/agent-sdk.html and surfaced in the app.
  • run --sdk-model, the model slug in every SDK run name, the full id as MLflow param and tag, and a model-swap table on both surfaces that pairs each model against the reference from the committed CSVs.

not done, on purpose

  • Serving is untouched. Wiring the SDK into the streamed event contract, the demo pack and container billing is a separate plan.
  • The sealed holdout stays sealed until a release decision.
  • The pipeline-on-Claude half of the model confound stays unisolated while the subscription-only rule holds; the session-side half is measured (section 06).
  • No Haiku-targeted optimisation was run, by instruction — the swap is a scoring pass only.
  • The next experiment worth running is a bigger train draw, not another prompt edit. Campaign s02 with --train-reports 300 would give the teacher ~100 first-wrong cases instead of ~34 and settle whether the distilled prompt is genuinely at its ceiling or the loop was simply under-powered. The 56 banked diagnoses carry over. Costs roughly 3× the wall clock per cycle on the subscription.
The recommendation, once more, with its boundary.

Adopt agent_sdk as the runtime direction: the evidence is strong, paired, and passes the strict rule on the split this project has always used. Do it knowing three things — the throughput cost is ~2.3× wall clock and one subprocess per conversation; the prompt it runs is the DeepSeek campaigns' output, so that work is a dependency and not a sunk cost; and its own optimisation loop has not yet been given enough failures to say whether the prompt can be improved further. The next honest step before anyone calls this a production decision is a confirmatory read on unseen conversations.

Design: the project's own design system — the dark IBM Plex tokens shared by artifacts s04–s10 in this repository. Every measured figure is read from a committed prediction CSV or the tracking store; the human and paper figures are published values from Chen et al. 2022, "ConvFinQA: Exploring the Chain of Numerical Reasoning in Conversational Finance Question Answering", and are labelled as such wherever they appear.
