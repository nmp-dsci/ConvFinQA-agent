s11 · results & runtime decision · branch agent-sdk-experiment · 2026-09-06

One Claude session beat four tuned DeepSeek agents — and its first prompt was its best

The Agent SDK arm answers the same 349 gate questions as the pipeline, through the same evaluator, the same paired significance rule and the same append-only record. It scores 90.54% against the optimised pipeline's 81.66%. The whole gain sits on the turns that require arithmetic. The prompt that achieved it was written once, by distilling the pipeline's four tuned prompts into one, and the optimisation loop that produced the pipeline's own champion could not improve on it.

Move the runtime to agent_sdk.

04 · The two architectures

multi-agent · what runs today

v8deepseek-v4-flashpydantic-ai

Four stateless agents in a fixed Python-controlled order: triage decides the turn type, preprocess writes sub-questions and a symbolic program, the retriever pulls each operand, the calculator executes through six tools. History is re-rendered into a text block on every turn because no agent holds any.

Four prompt lineages, ~22k characters total, each tuned separately across three campaigns. One experiment moves exactly one prompt, so every champion move has a named cause.

agent_sdk · the challenger

sdk_v1claude-sonnet-5claude_agent_sdk

One Claude session per conversation. The report arrives in the first message, each later turn is just the next question, and the session already holds its own prior tool calls and answers. The six calculator functions are its only tools — triage, planning and retrieval are a train of thought it follows and reports, not a pipeline it is pushed through.

One prompt lineage, 16.4k characters. It reports its stages in a structured result, so the same gold-derived panel and the same first-fault attribution apply with no new scoring code.

Nothing forces the trail, and that is measured too.

A program turn that reports no plan is counted as a preprocess skip; one that answers with no calculator call is a calculator skip; an answer matching no tool return is counted as inline arithmetic. Across 349 questions sdk_v1 recorded 3 stage skips and 5 inline-arithmetic answers — small enough to report as a finding rather than a defect, and visible rather than assumed.

05 · Distillation was the peak, and the loop could not beat it

The first SDK prompt was not hand-written. The teacher agent read the pipeline's four tuned v8 prompts plus the dataset notes and distilled them into one document with the train of thought as its spine — dropping the inter-agent plumbing that only exists because the pipeline's agents cannot see each other. That distillation, never optimised, is the 90.54%.

Then the same loop that produced v8 was pointed at it. One experiment completed:

A second experiment was attempted and died at the rewrite step on a subscription session limit, writing no version and no verdict — the append-only ledgers recorded the diagnosis work and nothing false. The campaign is capped at 2 experiments for this arm, so s01 is closed with sdk_v1 still champion.

The interesting result is not that the loop failed — it is what the failure says.

The pipeline needed three campaigns and seven experiments to climb 77.08% → 81.66%. The SDK arm reached 90.54% with a prompt written once, and the loop's best attempt made it worse. Read together: the knowledge in those four tuned prompts transferred, and what the pipeline's campaigns had been buying was largely compensation for its own architecture — the inter-agent plumbing, the re-rendered history, the stateless hand-offs. Remove the architecture and much of the tuning becomes unnecessary rather than additive. With 33 wrong turns left, some of them suspect gold labels, there is also very little headroom left for a prompt edit to find.

06 · What made this measurable

The comparison is the deliverable here, more than either number. Two runtimes that share nothing — different provider, different process model, different control flow — were made comparable because the loop and the tracking store fix everything except the thing under test:

One fixed split

Both arms answer the same 349 questions from the same 100 reports, drawn from a committed manifest. Paired per question, so the test is on the same items and not on two samples.

One evaluator, one panel

The SDK agent reports its stages into the same capture shape the pipeline emits, so the same gold-derived metrics and the same first-fault attribution compute for both — zero new scoring code, zero judge calls.

One significance rule

Net positive and one-sided cluster-corrected McNemar below 0.05, clustered by conversation, with a bootstrap CI on Δ. The rule that rolled back three pipeline versions is the rule this passed.

One append-only record

Three ledgers — diagnoses, rewrites, gates — joined by ids, so any edit traces to the cases that motivated it and the verdict it earned. A crashed cycle wrote no phantom row.

Concretely: --runtime agent_sdk is a flag on run, diagnose, propose, cycle and gate-targeted. Everything after the capture dict is code both arms share. That is why swapping a runtime is a measurable claim here instead of an impression, and why the same harness can judge whatever comes next.

07 · Caveats, stated plainly

90.54% is above the paper's human expert figure, on a public dataset.

Human expert execution accuracy is 89.44%. ConvFinQA is public and any frontier model may have seen it, so contamination cannot be excluded and the absolute number is not a generalisation claim. Two things soften it without settling it: program accuracy is only 0.409, so the agent is not reproducing gold programs, and the paired comparison stays fair because both arms face the same exposure. Our figures are also on a split drawn from the train pool, not the paper's test set.

Model and architecture changed together, and the confound was not isolated.

The pipeline runs DeepSeek v4-flash; the SDK arm runs Claude Sonnet 5. Isolating "Claude vs DeepSeek" from "one agent vs four" required a pipeline pass on the same Claude model, which needs an API endpoint — and this project runs the SDK on the subscription only, by decision. So the two factors remain confounded by construction. A win on effort is demonstrated; "one agent beats four" is not.

Two smaller ones.

The gate split has now judged around a dozen comparisons, so mild selection pressure exists; the sealed holdout is the only clean confirmatory read left and was deliberately not opened for an experiment. And neither arm is deterministic — the bootstrap CI absorbs that, and every number here is read from a committed CSV rather than a re-run.

08 · What ships next

done in this branch

  • The agent_sdk runtime, one session per conversation, calculator-only tools.
  • Its own diagnosis and teacher agents, and its own prompt lineage sdk_prompts.
  • Three append-only ledgers, backfilled over the pipeline's history.
  • Rate-limit refusals treated as unscored rather than wrong, and --resume-from to finish a throttled pass.
  • The comparison published to docs/optimization/agent-sdk.html and surfaced in the app.

not done, on purpose

  • Serving is untouched. Wiring the SDK into the streamed event contract, the demo pack and container billing is a separate plan.
  • The sealed holdout stays sealed until a release decision.
  • The model confound stays unisolated while the subscription-only rule holds.
  • A second SDK campaign (s02) could reuse the 56 banked diagnoses — but the evidence says prompt edits are not where the remaining headroom is.
The recommendation, once more, with its boundary.

Adopt agent_sdk as the runtime direction: the evidence is strong, paired, and passes the strict rule on the split this project has always used. Do it knowing the throughput cost is ~2.3× wall clock and one subprocess per conversation, and that the next honest step before anyone calls it a production decision is a confirmatory read on unseen conversations.

Design: the project's own design system — the dark IBM Plex tokens shared by artifacts s04–s10 in this repository. Every measured figure is read from a committed prediction CSV or the tracking store; the human and paper figures are published values from Chen et al. 2022, "ConvFinQA: Exploring the Chain of Numerical Reasoning in Conversational Finance Question Answering", and are labelled as such wherever they appear.
